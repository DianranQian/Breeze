# BSN 渐进式接入计划

> **本文档混合了三类内容，阅读时请先分清**：
>
> 1. **已验证的事实** —— 每条都指向源码位置或测试名，可以当场复核；
> 2. **已完成的实现** —— 代码在仓库里，测试在跑；
> 3. **未做的事与准入条件** —— 明确标注为"未实现"，不含任何"应该没问题"的推测。
>
> 基线：`04e1507` 之后的持续开发分支。锁定引擎版本 **Bevy 0.20.0**
> （`Cargo.lock` 实测，见 `Cargo.lock` 中 `name = "bevy"` / `version = "0.20.0"`）。
>
> **一句话结论**：Bevy 0.20 提供的是**编译期 Rust 代码里的场景描述**（`bsn!` 宏）
> 与**运行时实例化 API**（`spawn_scene`），**没有** `.bsn` 文件格式、没有加载器、
> 没有热重载、没有运行时文本解析。因此本轮做的是
> "**官方 BSN 实例化 → 提取为 `scene_doc` 文档 → 进入既有编辑器管线**"
> 这一条**单向、可测、可回退**的通道，而**不是**场景格式迁移。

## 1. 当前 Bevy 版本支持的 BSN 能力

### 1.1 权威依据（不是记忆，不是旧版本示例）

以下结论全部来自**本机锁定版本的实际源码**：

```
C:\Users\<用户>\.cargo\registry\src\index.crates.io-1949cf8c6b5b557f\
    bevy_scene-0.20.0\
    bevy_scene_macros-0.20.0\
    bevy_macro_utils-0.20.0\
```

对照的 `Cargo.lock` 条目为 `bevy 0.20.0`。文档站上的 `latest` 版本可能与锁定版本
不一致，因此**以源码为准**。

### 1.2 官方已提供（已实测可用）

| 能力 | 说明 | 本项目验证位置 |
| --- | --- | --- |
| `bsn!` 宏 | Rust 源码里声明一个实体及其组件、子级、观察者 | `crates/bsn_bridge/tests/官方场景原型.rs` |
| `bsn_list!` 宏 | 多个根实体，共享一个名字作用域 | 同上 `bsn_list_产生多个根实体` |
| `#名字` 语法 | 自动插入 `Name` 组件，并在同一宏内提供实体引用 | 同上 |
| `Children [ a -- b ]` | 构造层级；`--` 分隔实体 | 同上 `层级关系双向成立且子级有序` |
| 组件**补丁**语义 | `组件 { 字段: 值 }` 只改指定字段，其余保留 | 同上 `组件补丁是合并不是整体替换` |
| 值位置放表达式 | `{ expr }`、变量、函数调用 | `crates/bsn_bridge/src/template.rs` 的 `带参数模板` |
| `World::spawn_scene` | 立即解析 + 实例化，返回根实体 | `crates/bsn_bridge/src/host.rs` |
| `World::queue_spawn_scene` | 等待资源依赖加载后，在 `SpawnScene` 调度里实例化 | 仅记录，未采用（见 §1.5） |
| `#[derive(SceneComponent)]` | 把场景封装成可复用、可传 props 的组件 | 官方有；**本项目尚未定义任何 `SceneComponent`** |

**无窗口可用性**已实测：实例化只需要 `TaskPoolPlugin` + `AssetPlugin` + `ScenePlugin`，
不需要窗口与 GPU。全部 **65 项新增测试**都在无窗口环境下运行（明细见 §11）。

### 1.3 官方未提供（本轮**没有**伪造替代品）

| 缺失能力 | 官方源码原话 / 位置 |
| --- | --- |
| `.bsn` 文件资产格式 | `bevy_scene-0.20.0/src/lib.rs:854` —— “Bevy does not currently have support for `.bsn` files, but intends to offer a `.bsn` asset format in future releases.” |
| `.bsn` 文件加载器 / `AssetLoader` | 依赖上一项；格式本身不存在 |
| 在 `bsn!` 里引用外部场景文件 `:"scene.bsn"` | `bevy_scene_macros-0.20.0/src/lib.rs` 语法表该行标注 **“Asset format not yet implemented!”** |
| 场景包含的缓存 `:scene()` / `:MySceneComp` | 同上标注 **“Caching for scene includes not yet implemented!”** |
| `.bsn` 热重载 | 依赖 `.bsn` 格式 |
| 运行时把场景文本解析成场景 | `bsn!` 是编译期 proc macro；0.20.0 无文本解析器 |

**这一条必须反复强调**：不能因为 `bsn!` 宏能构建场景，就宣称 Bevy 已经提供了
成熟的 `.bsn` 文件编辑、加载、保存与热重载管线。**本轮没有任何代码读取或产出
`.bsn` 文件。**（可执行证据：`crates/bsn_bridge/src/capability.rs` 的测试
`官方_bsn_文件格式在_0_20_0_仍未提供`。）

### 1.4 两条影响本项目命名约定的实测约束

这两条不在常见教程里，是我们实测撞出来的，已写入能力清单并配了回归测试。

#### 约束一：中文命名的组件类型不能直接写进 `bsn!`

`bsn!` 区分"类型"与"值/函数"的依据是**标识符首字符是否大写**：

```rust
// bevy_macro_utils-0.20.0/src/path_type.rs:30
if last_ident_first_char.is_uppercase() { PathType::Type } else { PathType::Function }
```

汉字没有大小写，`char::is_uppercase()` 返回 `false`，于是 `Sprite属性`
这类中文类型名会被当成"从同名变量取值"，编译期报
`cannot find value ... in this scope`。

更隐蔽的是后续症状：写 `中文类型 { 字段: 值 }` 时类型已被当成表达式消费掉，
紧跟的 `{}` 被当成新的场景条目解析，于是报出**与中文毫无关系**的
`expected identifier`，很容易被误判成"中文字段名不支持"。

**实测结论与采用的两条绕法**（`crates/bsn_bridge/tests/标识符约束.rs`）：

| 情形 | 是否可行 | 说明 |
| --- | --- | --- |
| ASCII 类型名 + **中文字段名** | ✅ 可行 | 限制只在**类型名**上，字段名照旧用中文 |
| 中文类型名经**变量**插入 | ✅ 可行 | `let 实例 = 组件{..}; bsn! { 实例 }` |
| 中文类型名直接写 `中文类型 { 字段: 值 }` | ❌ 不可行 | 会被判为函数值 |

本项目的选择：**不为了迁就宏而重命名既有组件类型**（那会破坏注册表与旧场景文件），
而是在 `editor_app/src/bsn_templates.rs` 里统一采用"变量插入"。

#### 约束二：无法按名字枚举实体上的组件

`ComponentInfo::name()` 返回的 `DebugName` 只在 `bevy_utils/debug` 特性开启时
才是真实名字，否则内容是 `"<Enable the debug feature to see the name>"`
（实测见开发过程记录；`bevy_utils-0.20.0/src/debug_info.rs:100-127`）。
本工作区未开启该特性。

因此适配层**不依赖组件名枚举**，改用 **`TypeId` 白名单匹配**：

* 已支持组件：靠 `组件提取器` 声明的 `TypeId` 识别；
* 引擎派生组件：靠显式忽略清单识别；
* 其余：一律判为"未转换"，报告里给出 `TypeId`（开发者可用
  `TypeId::of::<可疑类型>()` 对照）。

这样做的好处是"宁可报错也不静默丢"，代价是诊断信息里没有可读类型名。
这条取舍记录在 `capability.rs` 的 `component_name_enumeration` 条目里。

### 1.5 为什么只用 `spawn_scene` 而不用 `queue_spawn_scene`

当前原型模板**不含外部资源依赖**（不引用图片/模型/其他场景），
`spawn_scene` 的立即路径足够。`queue_spawn_scene` 需要跑帧循环等待加载，
对"生成模板文档"这种同步操作不必要。

等将来模板要包含贴图/场景引用时，应改为排队路径，并让生成过程变成
异步或"先返回占位文档、加载完再补"。**这是明确的未完成项，不是已支持项。**

## 2. 现有 `scene_doc` 的职责与真实格式

这一节回答"我们的家底到底是什么"，因为渐进式接入的前提是**不动地基**。

### 2.1 数据模型

```
场景文档
├── 格式版本: u32                      // 当前 = 1
├── 元数据: 场景元数据
│   ├── 场景标识: 实体标识(UUID)
│   ├── 场景名: String
│   ├── 保存时间: Option<u64>
│   └── 自定义: BTreeMap<String, 属性值>
├── 实体表: BTreeMap<实体标识, 场景实体>
│   └── 场景实体
│       ├── 标识: 实体标识(UUID v4)      // 稳定身份
│       ├── 名称: String                 // 允许重名，唯一性由 UUID 保证
│       ├── 父实体: Option<实体标识>      // 父指针，层级是隐式的
│       ├── 次序: u32                    // 兄弟间顺序
│       ├── 变换: Option<变换数据>        // 平移/旋转四元数/缩放
│       ├── 组件: Vec<组件数据>           // 类型名 + BTreeMap<属性名, 属性值>
│       └── 编辑器隐藏 / 编辑器锁定 / 编辑器展开
├── 顶层顺序: Vec<实体标识>
└── 资源表: BTreeMap<项目相对路径, 资源引用>
```

关键设计（源码：`crates/scene_doc/src/document.rs`）：

* **扁平实体表 + 父指针**，而不是嵌套 `children`：拖放改层级、重命名、
  撤销 diff、按 ID 查找都是嵌套结构的最坏情况。层级一致性由
  `场景文档::校验()` 以 O(n) 保证。
* **UUID 身份与位置解耦**：删中间实体不会让其它引用错位。
* **`属性值` 是封闭枚举**（布尔/整数/浮点/文本/二维/三维/四维/颜色/枚举/
  资源/列表/结构/空），因此与 Rust 类型、与引擎类型都解耦。
* **`scene_doc` 不依赖 Bevy**，可在无 GPU、无窗口环境读写与测试。

### 2.2 序列化格式（实测，不是假设）

| 项目 | 事实 | 源码 |
| --- | --- | --- |
| 格式 | **RON 美化文本** | `crates/scene_doc/src/storage.rs` 的 `编码场景` |
| 扩展名 | **`.scene.ron`** | `storage.rs` 的 `默认场景扩展名` |
| 编码细节 | `struct_names(false)`、`depth_limit(32)`、`new_line("\n")` | `编码场景` |
| 为何美化 | 场景文件要进 Git，一行一字段才能让 `git diff` 有意义 | 同上注释 |
| 写入原子性 | 三段式：写 `.tmp` → 原名改 `.bak` → `.tmp` 就位；失败回滚 | `文件系统场景存储::写入` |
| 读取回退 | 原文件 → `.bak` → `.tmp`，每个候选都必须完整解析成功 | `文件系统场景存储::读取` |
| 版本过新 | **拒绝加载**，不做"尽力解析" | `场景错误::版本过新` |
| 未知字段 | 字段级 `#[serde(default)]`；未知组件与未知属性**原样保留** | 既有测试 `未知的组件属性被原样保留` |

**注意**：`格式版本` 的存在是为了"语义变更"（单位变化、层级表示变化）。
加字段不升版本，靠 `serde(default)` 兼容；读到更高版本直接拒绝，
因为"看不懂的新语义"强行解析必然在保存时丢数据。

### 2.3 文档 ⇄ ECS 的既有桥接

`crates/editor_app/src/scene_bridge.rs`：

* `构建世界(世界, 文档, 注册表) -> (构建统计, 实体映射表)`
  —— **单向**：文档 → 世界。运行时修改**不会**自动回写文档。
* 两趟：先建全部实体与组件，再按文档父关系插 `ChildOf`
  （文档顺序不保证父在子之前）。
* `插入已知组件` 把文档组件名映射到具体 Bevy 组件；
  注册表里有而这里漏了分支会被统计成"跳过"，有测试
  `注册表与插入分支一一对应` 守住。
* 组件能力的唯一扩展点是 `组件注册表` + `组件类型` trait
  （`组件名`/`默认实例`/`字段描述`/`导出`/`实例化`）。
  当前注册 **4 个**：`Transform`、`Visibility`、`Sprite`、`Camera2d`。

### 2.4 撤销重做如何配合文档

`editor_core::撤销栈` + `编辑器命令`：命令作用于**文档**，
撤销是反向命令，不是文档深拷贝快照。因此只要新数据最终变成
`场景文档`，它自动获得精确的撤销重做与"未保存修改"检测。

**这正是本轮选择"提取成文档"而不是"直接生成运行时实体"的根本原因。**

### 3.2 实际运行的 BSN 场景示例

取自 `crates/editor_app/src/bsn_templates.rs`（可运行、被测试覆盖）：

```rust
let 主相机 = 编辑器相机2d { 正交半高: 360.0 };   // 中文组件类型 → 变量插入
let 玩家 = Sprite属性 {
    贴图路径: 项目相对路径::解析("textures/玩家.png").ok(),
    颜色: 颜色值::srgb(0.30, 0.68, 1.0, 1.0),
    自定义尺寸: Some((48.0, 48.0)),
    ..Default::default()
};

在世界上实例化(世界, bsn! {
    #二维关卡
    Transform { translation: { Vec3::new(0.0, 0.0, 0.0) } }
    Children [
        #主相机
        主相机
        Transform { translation: { Vec3::new(0.0, 0.0, 1000.0) } }
        --
        #背景板
        背景板
        Transform {
            translation: { Vec3::new(0.0, 0.0, -10.0) },
            scale: { Vec3::new(8.0, 4.5, 1.0) }
        }
        --
        #玩家
        玩家
        Transform {
            translation: { Vec3::new(0.0, -80.0, 0.0) },
            rotation: { Quat::from_rotation_z(0.15) },
            scale: { Vec3::new(1.0, 1.0, 1.0) }
        }
        Visibility::Visible
    ]
})
```

它覆盖了原型要求的最小集合：**4 个实体、名称、位置/旋转/缩放、
两层层级、以及本项目自己注册的组件（`Sprite属性`、`编辑器相机2d`）**，
外加一条资源引用。

### 3.3 转换支持范围（逐字段，有测试）

| `scene_doc` 字段 | 来源 | 转换类型 | 测试 |
| --- | --- | --- | --- |
| `名称` | `Name` 组件 | **无损** | `完整转换_名称变换层级与次序逐项核对` |
| `名称`（缺 `Name`） | 自动命名 `未命名实体N` | **规范化**，记入报告 | `缺少名称时自动命名并记录规范化` |
| `变换.平移/旋转/缩放` | `Transform` | **无损**（四元数归一化） | `变换转换保留全部十个分量` |
| `父实体` + `次序` | `Children` / `ChildOf` | **规范化**（关系 → 父指针+序号） | `完整转换_…`、`层级关系双向成立且子级有序` |
| `组件`（`Sprite`） | `Sprite属性` | **无损**（经 `组件类型::导出`） | `组件字段值逐项核对` |
| `组件`（`Camera2d`） | `编辑器相机2d` | **无损** | `BSN模板生成的文档能构建出正确的运行时世界` |
| `组件`（`Visibility`） | Bevy `Visibility` | **有损/规范化**：三态→布尔 | `世界类型与文档类型不同的组件经转换器接入` |
| `资源表` | 组件属性里的资源引用 | **规范化**（`同步资源表` 登记） | `BSN模板生成的文档能构建出…` 里校验资源表 |
| `标识` | 新建 UUID v4 | **新身份**，不复用 `Entity` | `实体身份是新的唯一标识且不复用运行时实体` |
| `编辑器隐藏/锁定/展开` | —— | 恒为默认 `false` | 无（见 §3.4） |

### 3.4 明确**不**支持、且会报错而不是丢弃的内容

| 内容 | 行为 | 测试 |
| --- | --- | --- |
| 未登记提取器的组件 | 报告 `未转换组件`；`提取并校验` **返回错误** | `未登记组件导致严格转换失败而不是静默丢弃` |
| 注册表里没有该组件名 | **返回错误**，不跳过 | `注册表缺组件时报错而不是跳过` |
| 无 `Rust` 类型的动态组件 | 计为未转换 | `extract.rs` 内部分类逻辑 |
| 编辑器元数据（隐藏/锁定/展开） | 不来自 ECS，恒为默认 | 已知限制 |

### 3.5 有意忽略（引擎派生，不算丢失）

| 组件 | 为什么可以忽略 |
| --- | --- |
| `GlobalTransform` | 是 `Transform` 沿层级累积的结果，运行时由 Bevy 维护。写进文档反而会产生两份矛盾的坐标 |
| `TransformTreeChanged` | 变换传播用的内部标记 |
| `InheritedVisibility` | `Visibility` 的必需组件，由可见性与层级推导 |
| `ViewVisibility` | 同上 |

这张清单是**白名单性质**的：新增任何条目都必须能说清"它为什么能从已有数据重建"，
否则就是在用"忽略"掩盖数据丢失。

**已知有损项（已在字段提示里写明）**：`Visibility::Visible` 经文档层往返后
变成 `Visible → 可见=true → Inherited`。因为文档只存布尔，这是既定设计，
不是本轮引入的问题，但 BSN 接入会**放大**它的可见性，值得后续评估。

### 3.6 一个必须说清的方向性限制

```
编译期 BSN 描述  ──✅──▶  真实 ECS  ──✅──▶  scene_doc 文档
scene_doc 文档   ──❌──▶  任意形状的 bsn!       （编译期宏，无运行时解析）
scene_doc 文档   ──⚠️──▶  预定义形状 + 运行时数值  （带参数模板，形状写死）
```

第三行是唯一"看起来像反向"的东西：`带参数模板` 允许名称、平移、缩放
来自运行时数据，但**实体个数、层级形状、组件种类集合全部是编译期固定的**。
这不是"把用户场景转成 BSN"，只是"用写好的 BSN 形状承载运行时数值"。

## 5. 采用官方 `.bsn` 文件之前的必须条件

以下每一条都必须**先被满足**，才值得启动全面迁移评估。任何一条不满足，
继续保留现有 RON 格式就是正确决策。

### 5.1 官方侧硬条件

- [ ] 官方 `.bsn` **文件格式规范**正式发布（不是"计划中"）；
- [ ] 官方提供 **`AssetLoader`**，能把 `.bsn` 加载为可实例化场景；
- [ ] 该 API 与项目锁定的 Bevy 版本兼容（不是需要整体升级才能用）；
- [ ] `bsn!` 与 `.bsn` 文件**语法一致性**经官方文档确认（官方目前只说
      "broad syntactic compatibility"，这还不够作迁移依据）；
- [ ] 官方明确 **`.bsn` 不支持表达式**的后果与替代方案。

### 5.2 表达能力条件

- [ ] 能表达项目的**实体身份**需求（或给出稳定 ID 机制）；
- [ ] 能表达**层级**（`Children`/`ChildOf` 已有，需确认文件格式同样支持）；
- [ ] 能表达**变换**（`Transform` 三件套）；
- [ ] 能表达**资源引用**（路径或 GUID；本项目文档同时存路径与 UUID）；
- [ ] 能表达**本项目的全部受支持组件**，或提供注册扩展点；
- [ ] 对**编辑器专有元数据**（隐藏/锁定/展开、自定义键值）有明确处理方案
      （放进 `.bsn`？放伴随文件？还是承认必须由编辑器侧旁路保存？）。

### 5.3 工程体验条件

- [ ] **热重载**与错误诊断满足编辑需求（错误要能定位到行列）；
- [ ] **保存**语义明确（编辑器能否写 `.bsn`？还是只读？）；
- [ ] **Git 差异**可读（一行一字段或等价的可评审性）；
- [ ] 解析性能在真实规模场景下可接受。

### 5.4 数据安全条件

- [ ] **旧文件可迁移**，且有自动化迁移测试；
- [ ] 迁移过程**不静默丢数据**（未知组件必须保留或明确报错）；
- [ ] 实体身份在迁移后保持稳定（否则外部引用全断）；
- [ ] 资源引用在迁移后仍可解析；
- [ ] 迁移失败时可**回退**到旧格式。

### 5.5 试点条件

- [ ] 用**一个真实项目**（不是玩具场景）跑通：打开 → 编辑 → 保存 →
      **退出重启** → 再打开 → 运行 → 结果一致；
- [ ] 该试点的撤销重做、2D/3D 一致性、示例项目全部通过。

**只有上述全部勾选，才建议启动"全面迁移评估"。** 仅仅因为某个新版出现了
`.bsn` 加载 API，**不构成**删除现有格式的理由。

## 6. 如何判断未来官方格式"成熟到值得采用"

给一个可操作的判据，避免凭感觉决策。

| 维度 | 不成熟的表现 | 成熟的表现 |
| --- | --- | --- |
| 格式稳定性 | 官方反复改语法，且无版本协商机制 | 有格式版本号 + 兼容策略 |
| 工具链 | 只有宏，无文件 loader | 有 loader + 诊断 + 热重载 |
| 表达能力 | 缺编辑器必需的数据类别 | 本节 §5.2 全绿 |
| 生态 | 无第三方编辑器支持 | 有成熟编辑器/工具在用 |
| 迁移成本 | 需改写全部既有文件且无法回退 | 有双向或可回退路径 |
| 官方态度 | "intends to offer"（计划） | 已发布 + 有弃用/迁移政策 |

**当前状态**：格式稳定性 = 无（格式不存在）；工具链 = 仅宏；
官方态度 = "intends to offer in future releases"。因此**远未成熟**。

### 6.1 触发重新评估的信号

任一出现即应重新读源码、更新 `capability.rs`、并重跑准入清单：

1. `bevy_scene` 出现 `.bsn` 相关的 `AssetLoader` 实现；
2. `bsn!` 语法表里 `:"scene.bsn"` 的 "not yet implemented" 警告消失；
3. `ScenePlugin` 注册了新的资产类型或文件扩展名；
4. 官方发布迁移指南或格式规范文档。

**本项目已经内置守卫**：`capability.rs` 的测试
`官方_bsn_文件格式在_0_20_0_仍未提供` 会锁定这几条关键事实，
`能力清单与锁定版本一致` 会在 Bevy 版本变化时立即失败。
也就是说**升级 Bevy 会强制维护者重读本文档与能力清单**。

## 7. 未来迁移时如何保留现有场景文件

原则：**现有 `.scene.ron` 是用户的资产，不是内部实现细节。**

1. **永不原地覆盖**：迁移产出新文件（或双写），旧文件保留至少一个大版本；
2. **双向期**：读取支持两种格式；写入默认仍是 RON，直到试点全绿；
3. **显式迁移命令**：把"转换整个项目"做成用户可触发的动作，
   而不是打开项目时静默批量改写；
4. **迁移报告**：逐文件列出"无损 / 规范化 / 有损 / 无法迁移（原因）"；
5. **可回退**：迁移前的文件保留在 `.bak` 或迁移快照目录；
6. **版本协商**：项目清单里记录"本项目场景格式"，混用时不猜。

### 7.1 本次原型已经为此打好的基础

* `bsn_bridge` 的 `提取报告` 已经是"无损 / 规范化 / 忽略 / 未转换"四分类模型，
  迁移报告可以直接复用它；
* `bsn_bridge` 已给出**单一入口**（`从模板生成文档` / `提取并校验`），
  未来换成 `.bsn` loader 时，改的是"场景来源"，不是整个编辑器；
* `editor_app` 与 BSN 的接触面**只有 `bsn_templates.rs` 一个模块**，
  未来替换成本被限定在一个文件内。

## 8. 测试策略：旧文件迁移、身份、组件完整性、资源引用

| 关注点 | 现在怎么测 | 未来迁移要加什么 |
| --- | --- | --- |
| 旧文件迁移 | 既有 `缺少可选字段的旧版本场景仍可加载`、`版本过新的场景被拒绝加载` | 每条旧版本样例一份固定 fixture，断言迁移后逐字段相等 |
| 实体身份 | `实体身份是新的唯一标识且不复用运行时实体`、`BSN模板生成的文档实体身份稳定且唯一` | 迁移前后 UUID 映射表必须一对一且全部命中 |
| 组件完整性 | `未登记组件导致严格转换失败`、`注册表缺组件时报错`、`组件字段值逐项核对` | 对每个样例做"输入组件集合 == 输出组件集合"的集合断言 |
| 资源引用 | `BSN模板生成的文档能构建出…` 中的资源表断言；既有 `资源改名会同步更新所有引用` | 迁移后逐条解析资源是否存在，并校验 UUID 可重建 |

| 不污染用户文件 | `生成模板文档不写任何文件` | 迁移失败时必须验证原文件字节级未变 |

**反面要求（明确禁止）**：不能把"实体数量相等"当成往返测试。
本次每个转换测试都核对了名称、变换分量、层级、次序与组件字段值。
