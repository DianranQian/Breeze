# 微风 下一阶段开发路线图

> **本文档是计划，不是现状。** 现状事实见 [`项目现状总览.md`](./项目现状总览.md)。
> 基线：`193bf26`。所有"当前基线"均可在源码中找到对应位置。
>
> 撰写原则：
> 1. 优先修复会让**已有功能不可靠**的问题，而不是增加新面板；
> 2. 每个里程碑都要能独立验收、独立提交；
> 3. 依赖未就绪就不排进当前阶段（例如三维 gizmo 依赖鼠标注入验收能力）。

## 0. 结论摘要

**产品定位（基于现状的判断）**：微风 已经是一个**可用的 2D 游戏场景编辑器**
（场景树 + Inspector + 视口 + 资源 + 撤销 + 保存/加载 + 运行观察 + 代码编辑 + 主题/工作区/双语），
并以 3D 观察、运行观察和代码编辑作为**辅助模式**。它还不是通用引擎，也不应该现在就去追。

**推荐的下一个开发任务（M1）：真实鼠标交互的端到端验收工具链。**
理由见第 3 节与第 4 节；一句话：**Dock/工作区是产品的地基，而地基目前只有数据路径测试**，
且这项能力是后续 3D gizmo、菜单、拖放等所有交互里程碑的公共前置。

紧接着的三个里程碑：**M2 三维变换 gizmo → M3 运行模式 Play-in-Editor 视口 → M4 代码诊断与多标签**。

## 2. 方向评估（A–G）

评分口径：用户价值 / 实现成本 / 风险 / 依赖，均为相对判断（S/M/L）。

| 方向 | 用户价值 | 成本 | 风险 | 依赖 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A 可靠性与交互闭环** | 高：护住地基，所有交互类功能的前置 | **S~M** | 低 | 无 | **立即做（M1）** |
| **B 专业编辑器体验** | 中高：菜单图标、快捷键、排版、对比度 | S~M | 低 | A（验证手段） | 与 A 并行小步做（M1.5/M4.5） |
| **C 真正 3D 编辑** | 高：决定"能不能做 3D 游戏" | M~L | 中（gizmo 拖拽需要指针验证） | A（鼠标注入）+ 现有变换数据 | **A 之后第一优先（M2）** |
| **D 脚本工作流** | 中：代码模式已有闭环，LSP 成本高 | M~L | 中（依赖第三方 LSP/解析器） | 无硬依赖 | 中期（M4，先诊断后 LSP） |
| **E 资产工作流** | 中高：导入/依赖是真实痛点 | M | 中（导入格式） | 无 | 中期（M7） |
| **F 运行调试** | 高：Play-in-Editor 是引擎体验核心 | L | 中高（渲染循环与编辑世界隔离） | 现有 `运行时宿主` | 中期（M3） |
| **G 原生多窗口** | 低~中：面板迁移是重度用户需求 | L | 高（Bevy 多窗口 + egui context 生命周期） | 需要原型 | **暂缓**（M8，先做 1 天原型再决定） |

### 2.1 为什么 3D（C）不是第一优先

3D 视口已经能**看**、能**选**、能改数值，但"在视口里拖 gizmo"这件事本质是**指针交互**；
如果连 Dock 拖拽都没有自动化验收，gizmo 的拖拽回归将完全无法守护。
因此 C 的价值要在 A 之后再兑现——不是"3D 不重要"，而是**顺序问题**。

### 2.2 为什么暂缓原生多窗口（G）

- `bevy_egui 0.43` 不处理 `ViewportCommand::CreateWindow`（已核对源码：无 viewport 命令分发）；
- 真正可行路径是"Bevy 第二窗口 + 独立 egui context"，这需要把每窗口的相机、context、
  输入、主题、Dock 表面迁移全部接起来，并解决"egui_dock 表面跨窗口迁移"这一非原生概念；
- 收益集中在重度用户的布局习惯，不是当前阶段的瓶颈。
- **结论**：不进当前阶段；在 M8 安排一个**限时原型**（第二窗口 + 一个 egui 面板），
  以实验结论决定是否投入，而不是先重构。

## 3. 里程碑规划

依赖关系：

```text
M1 鼠标验收工具链 ──┬──► M2 三维 gizmo ──► M2.5 三维多选/框选
                    ├──► M1.5 菜单图标/排版收尾
                    └──► M4 代码诊断与多标签
M3 Play-in-Editor 运行渲染（可与 M2 并行，依赖较少）
M5 资产元数据/依赖 ──► M6 导入管线
M7 模式一致性/组合矩阵回归（持续项，不单独占阶段）
M8 原生多窗口原型（限时，结论驱动）
```

### M1（推荐下一项）真实鼠标交互的端到端验收

| 项 | 内容 |
| --- | --- |
| 目标与价值 | 让 Dock/工作区的拖拽、分割线、关闭/重开、浮窗在 CI 中被真实指针事件验证；为后续所有交互功能提供可复用能力 |
| 当前基线 | `gui_probe` 已能定位窗口（Win32 `EnumWindows`+DPI）、启动应用、采集证据；**无指针注入**；Dock 数据路径测试 3 条 |
| 需要修改 | `crates/gui_probe`：新增 `input` 模块（`SendInput` 鼠标移动/按下/抬起/滚轮、坐标换算到客户区、DPI 校准、窗口前置）；CLI 增加 `drag`/`click` 子命令或脚本内的动作序列；`tools/gui_acceptance.ps1` 增加交互场景；必要时给应用加"只读的布局查询端点"（已有证据 JSON，无需新端点） |
| 前置依赖 | 无（Win32 API 已在 `windows-sys` 依赖内，需增加 `Win32_UI_Input_KeyboardAndMouse` 特性） |
| 技术风险 | ① DPI 与窗口边框导致坐标偏移 → 用"客户区原点 + 已声明的 per-monitor DPI"换算，并用截图断言校正；② 拖拽是连续事件，需要分步移动 + 稳定等待；③ `egui` 需要真实的按下-移动-抬起帧序列 → 注入节奏要慢于帧间隔（可用 `BEVY_STUDIO_CAPTURE_FRAME` 配合） |
| 最小可交付 | 一条可重复执行的脚本：拖垂直分割线 → 断言左右面板宽度比变化；拖标签到另一叶子 → 断言标签归属变化且面板不丢；关闭再打开面板 → 断言布局恢复；重启后断言布局持久化 |
| 验收条件 | ① 全部动作由真实指针事件完成（日志中能看到注入坐标与应用窗口客户区一致）；② 每个动作都有"操作前/后"两次真实截图 + 证据 JSON；③ 失败时能区分"注入没生效"（几何无变化 → 采集/工具失败）与"布局错误"（几何变化不符合预期 → 界面缺陷）；④ 退出码与现有 probe 一致（0/2/3） |
| 自动化测试 | `gui_probe` 单测：坐标换算、DPI 缩放、拖拽轨迹生成；`tools/gui_acceptance.ps1` 新增 `drag_*` 场景并纳入总通过条件 |
| 完成后用户能做什么 | 用户拖拽面板/分割线时，回归会被 CI 拦住；开发者拿到可复用的"真实指针"测试能力 |

### M2 三维变换 gizmo（视口内直接编辑）

| 项 | 内容 |
| --- | --- |
| 目标与价值 | 让 3D 模式从"看+改数值"变成"能在视口里拖动对象"，这是 3D 编辑的最小可信闭环 |
| 当前基线 | 三元变换数据完整；Inspector 三元编辑 + 四元数/欧拉互转（有测试）；3D 投影/拾取/网格已就绪；`UiAction::拖动实体到` 只处理 2D 世界偏移 |

### M3 运行模式：Play-in-Editor 渲染

| 项 | 内容 |
| --- | --- |
| 目标与价值 | "运行"变成真的能看到游戏画面，而不仅是统计 |
| 当前基线 | `运行时宿主` 用场景文档构建独立 `World`（有实体/组件/父子统计），状态机完整；预览渲染管线（渲染到纹理）已可复用 |
| 需要修改 | `scene_bridge.rs`：运行时相机与渲染目标（渲染到视口纹理，或分屏）；`preview.rs`：运行态下切换到运行时世界渲染；`actions.rs`：运行/暂停/停止与渲染生命周期绑定；`viewport_panel.rs`：运行时画面标识 |
| 前置依赖 | 无硬依赖（可与 M2 并行）；需要明确"编辑器世界 vs 运行时世界"的渲染隔离（现有 RenderLayers 经验可复用） |

| 最小可交付 | 点"运行"→ 视口显示运行时世界（精灵/网格按场景构建）→ 暂停冻结 → 停止恢复编辑预览 |
| 验收条件 | GUI：运行态截图中出现运行时内容且与编辑态不同（probe 断言视口区域像素变化）；运行时实体数与文档一致；停止后恢复原预览 |
| 完成后用户能做什么 | 在编辑器内直接看到场景运行画面 |

### M4 代码工作流：诊断与多标签（先诊断，后 LSP）

- **M4a（S）**：多文件标签 + 文件树入口 + 未保存确认；
- **M4b（M）**：集成 `cargo check --message-format=json` 作为"诊断来源"（不引入 LSP），
  把错误映射到文件/行并在代码面板与状态栏展示；这是**成本可控且真实有用**的一步；
- **M4c（L，可选）**：评估 `rust-analyzer`（LSP）集成成本：进程管理、JSON-RPC、增量同步、
  与 egui 编辑器的坐标映射；若 M4b 已能满足"看得见错误"，LSP 可继续延后。
- 验收：headless 解析诊断 JSON → 行号定位；GUI：注入一条编译错误，代码面板显示红色标记与状态栏计数。

### M5/M6 资产：元数据、依赖与导入

- M5（M）：资源元数据（类型、尺寸、引用计数）+ 依赖追踪（哪些场景引用该资源）+ 删除前引用警告；
- M6（L）：导入管线（复制到项目 `assets/`、生成 `.meta`、失败回滚）。
- 验收：删除被引用资源时给出具体场景/实体列表；导入图片后立即可拖入场景且元数据正确。

### M7 模式一致性与组合矩阵回归（持续项）

- 每次里程碑结束跑"五模式 × 三主题 × 中英文 × 重启"矩阵（probe 已支持 env 覆盖）；
- 新增集成测试：`编辑 → 切模式 → 切回` 后文档修订号/选择/撤销栈不变；
  `3D 选中 → 切代码 → 切回` 选择仍在；`改主题 → 切布局` 主题不变。
- 该项不单独占阶段，但**每个里程碑的 DoD 都包含它**。

### M8 原生多窗口限时原型（结论驱动，不预先承诺）

- 目标：验证"Bevy 第二窗口 + 独立 egui context"是否可用（限时，产出实验报告 + 最小 demo）；
- 若可行：再规划窗口间面板迁移（需要自定义 surface 归属，超出 egui_dock 原生能力）；
- 若不可行：给出源码级证据与替代方案（应用内浮窗 + 工作区预设），并把结论写入现状文档。

## 4. 推荐：从 M1 开始（为什么是它）

1. **风险最高、成本最低**：Dock 是产品地基，当前只有数据路径测试；而注入指针只需要 Win32
   `SendInput`（现有 `windows-sys` 依赖内），不需要改生产代码架构；
2. **杠杆最大**：M1 产出的能力被 M2（gizmo 拖拽）、M1.5（菜单交互）、M5（拖放导入）直接复用；
3. **不可替代**：任何"看起来能用"的交互，没有真实指针验证就只是开发者的一厢情愿——
   项目已经因为"不可靠截图"吃过一次亏（`PrintWindow`），不该在交互上重复同类错误；
4. **不阻塞其他线**：M1 期间可以并行做 M1.5 的菜单图标与 M3 的运行时渲染（互不冲突）。

### M1 的完整验收标准（可直接作为任务书）

**功能**
- `gui_probe` 新增鼠标操作：移动到客户区坐标、按下、分段移动、抬起、滚轮；坐标支持逻辑/物理换算；
- 应用启动时自动前置窗口并等待稳定帧（复用现有 `BEVY_STUDIO_CAPTURE_FRAME`）。

**场景（全部由真实指针触发）**
1. 拖动垂直分割线 ≥ 80px：断言 `scene_tree` 与 `viewport` 宽度变化方向正确、比例在合理区间；
2. 拖动水平分割线 ≥ 60px：断言底部面板高度变化、视口高度反向变化；
3. 标签 A 拖到标签 B 所在叶子：断言 A 与 B 同属一个节点（证据 JSON 增加"标签归属"字段）；
4. 标签从组中拖出到视口边缘：断言新增分区（叶子数 +1）且面板不丢；
5. 关闭面板后用「窗口」菜单重新打开：断言面板回归且布局可用；
6. 浮动面板拖出并停靠回来：断言浮动表面数 1→0；
7. 保存工作区 → 重启 → 断言同一布局（复用 `restart_restore` 模式）。

**证据与判定**
- 每个动作前后各一份 PNG + 证据 JSON，存 `.verify/runs/drag_*/`；
- 判定分类：几何完全不变 → `capture_failed`（注入未生效）；几何变化方向/归属不符 → `ui_defect`；
- 汇总脚本输出通过/失败与失败原因，退出码沿用 0/2/3。

**自动化测试**
- `gui_probe`：坐标换算（含 150% DPI）、拖拽轨迹生成、按下-移动-抬起的时序状态机；
- 应用侧：`TabPath`/`NodePath` 归属查询（已有 `find_tab`，补一个"同叶判定"纯函数 + 测试）；
- 回归门禁：`tools/gui_acceptance.ps1` 全绿（含新增 drag 场景）才允许合并。

**完成定义（DoD）**
- 上述 7 个场景在中文/深色下全部通过；至少 1 个场景在英文/浅色下通过；
- 工作日志记录注入坐标、DPI、前后几何与判定；
- 独立 Git 提交，生产代码改动仅限必要的测试钩子（不得为测试改布局行为）。

## 5. 之后的 1–3 个里程碑与关系

| 顺序 | 里程碑 | 与前一里程碑的关系 | 复杂度 |
| --- | --- | --- | --- |
