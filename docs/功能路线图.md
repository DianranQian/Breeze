### 关于资源 UUID 的诚实说明

**结构已就位，功能未生效。**

`资源引用值 { 路径: 项目相对路径, 唯一标识: Option<Uuid> }`
这个结构、序列化、以及 `改资源路径` 时保留 UUID 的逻辑都已实现
（并有测试断言"改名不应丢失资源 UUID"）。

**但 `唯一标识` 在实践中总是 `None`**，因为没有任何代码去写它：
需要一个导入器在处理资源时生成 UUID 并持久化到元数据文件
（例如 `assets/textures/hero.png.meta`）。

因此"即使文件改名也能按 UUID 重连引用"这个**能力目前没有生效**。
当前改名能同步引用，靠的是路径层的 `改资源路径` 主动改写，
而不是 UUID 兜底。这是一个真实的功能缺口，不是设计缺陷。

### 为什么"游戏自己的逻辑"是里程碑 C 的核心缺口

当前 `运行时宿主::启动` 做的事情是：

```text
场景文档  ──>  新建 World  ──>  按文档 spawn 实体与组件  ──>  统计
```

它**没有**：

- 加载游戏项目的 Rust 代码（没有玩家的移动、碰撞、AI）；
- 建立 `Schedule` 并逐帧推进系统；
- 建立渲染管线把游戏画面显示出来。

所以现在能验证的是"场景能被正确构建成 ECS 世界"，
而不是"游戏能跑起来"。这两件事的差距就是里程碑 C 剩余的工作量。

### 热重载的分阶段实施

需求要求分阶段，并明确"不得声称可以无条件热重载任意 Rust 代码"。
下面是经过评估的分阶段方案与**真实限制**。

| 阶段 | 内容 | 可行性 | 状态 |
| --- | --- | --- | --- |
| 1 | 资源变更检测 | 高（`notify` 已选型） | ⛔ |
| 2 | 图片、音频等资源重新加载 | 高（`AssetServer` 支持 reload） | ⛔ |
| 3 | 场景重新加载 | 高（把文档重新构建进运行时世界） | ⛔ |
| 4 | Rust 代码增量编译与重载 | **低到中，有硬限制** | ⛔ |

#### 阶段 4 的真实限制（必须说清楚）

动态库热重载任意 Rust 代码**不能**无条件成立，原因有四：

1. **ABI 兼容性**：Rust 没有稳定的 ABI。跨动态库边界传递
   `Vec<T>`、`String`、`Box<dyn Trait>` 时，两个编译单元的
   类型布局与 monomorphization 可能不一致，导致未定义行为。
2. **状态迁移**：重载后旧的组件数据如何映射到新的类型定义？
   若结构体加了字段，旧实例的内存布局就不对了。
3. **资源所有权**：`Handle<T>`、`Asset` 的所有权在
   `AssetServer` 里；重载代码时这些句柄指向的资源由谁负责？
4. **系统注册**：`App` 的 `Schedule` 里已经构建好的系统图
   包含函数指针，指向旧动态库的代码段。重载后这些指针全部失效。

**可行的范围**（不是承诺，是需要实验验证的方向）：

- 把**游戏逻辑**放在动态库里，编辑器只提供稳定的宿主接口
  （用 `#[repr(C)]` 或明确的 vtable + 版本化接口，避免 Rust ABI）；
- 重载时**重建整个运行时世界**（阶段 3 的能力），
  用场景文档作为状态迁移的载体 —— 也就是说"热重载"实际上是
  "停止 → 重新编译 → 重新构建世界 → 运行"，用户感知接近无缝；
- 这能覆盖"改数值、改逻辑"的常见场景，
  **但不能**保留运行时的瞬时状态（例如玩家正跳到半空的位置）。

**本版本没有实现任何阶段**，上表的状态列全部是 ⛔。

## 八、演进方向：把游戏画面接进视口

这是当前最大的**观感**缺口，也是最有价值的下一个技术步骤。

### 现状

视口画的是**编辑器对场景的表示**：网格、坐标轴、实体包围框、
选中高亮。它不是把游戏画面渲染到纹理再贴上来。

### 为什么这么做（这是刻意的）

- 编辑器不依赖游戏相机与渲染管线就能工作；
- 场景数据的每一个改动都能立刻、确定地看到效果；
- 不存在"编辑器和游戏抢同一台相机"的问题；
- 使编辑闭环能被独立验证 —— 这一期的目标是"闭环可验证"。

### 代价

看不到材质的真实外观、看不到光照与动画。

### 演进方案（不需要改交互逻辑）

```text
1. 在编辑器主世界里加一台 Camera2d，渲染目标指向一张 Image 纹理
2. 视口面板把这张纹理作为底板绘制（egui::Image）
3. 编辑叠加层（网格 / 包围框 / Gizmo / 选中高亮）继续由 editor_ui 绘制
4. 视口相机的平移缩放映射到那台 Camera2d 的 Transform 上
```

第 3 步是关键：叠加层与底板分离，意味着**视口交互逻辑完全不用改**，
只是多了一层背景。`viewport_panel.rs` 的拾取、框选、拖拽全部基于
世界坐标与相机变换，与底板是什么无关。
