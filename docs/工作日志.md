## 阶段 1：生态调查——两次关键否决

这一步的目标是"**核实**依赖兼容性，而不是假定某个库还能用"。
方法：直接查 crates.io API 的版本与依赖要求，而不是凭记忆。

### 发现 3（否决一）：`bevy-inspector-egui` 与 Bevy 0.20 不兼容

```powershell
Invoke-RestMethod "https://crates.io/api/v1/crates/bevy-inspector-egui/0.37.0/dependencies"
```

```text
bevy_app     ^0.19.0
bevy_ecs     ^0.19.0
bevy_reflect ^0.19.0
bevy_egui    ^0.40.0
egui         ^0.34
```

而当前 `bevy_egui 0.43.1` 要的是 Bevy `^0.20.0` 与 egui `^0.36`。

**为什么不能"凑合用"**：Bevy 的子 crate 之间靠类型严格耦合。
若同时存在 Bevy 0.19 与 0.20，那么 `bevy::prelude::Transform` 与
`bevy_inspector_egui` 看到的 `Transform` 是**两个不同类型**，
根本无法互操作。这不是"可能有点问题"，而是必然编译失败或行为错乱。

**决定**：自行实现 Inspector，不引入该库。

### 发现 4（否决二）：`egui` 必须钉在 0.36，不能用最新的 0.37

crates.io 上 `egui` 最新是 **0.37.0**。直觉是"用最新版"。
但查两个下游库的依赖：

```text
bevy_egui 0.43.1  →  egui ^0.36
egui_dock 0.21.1  →  egui ^0.36
```

若写 `egui = "0.37"`，Cargo 会**同时**保留 0.36 与 0.37 两个 `egui`。
后果：`egui::Ui` 与 `egui::Context` 在类型层面变成两套互不兼容的类型，
`egui_dock` 的 `TabViewer::ui(&mut Ui, ...)` 签名与实际传入的 `Ui` 对不上，
报出一堆看似莫名其妙的类型错误。

**验证方式**（不是猜的，是查 `Cargo.lock`）：

```text
name = "egui"       version = "0.36.2"     ← 只有这一个
name = "bevy_egui"  version = "0.43.1"
name = "egui_dock"  version = "0.21.1"
name = "bevy"       version = "0.20.0"
name = "wgpu"       version = "30.0.1"
name = "winit"      version = "0.30.13"
```

```powershell
cargo tree -i egui --depth 1
```
```text
egui v0.36.2
├── bevy_egui v0.43.1
├── editor_app v0.1.0
├── editor_ui v0.1.0
└── egui_dock v0.21.1
```

三方收敛到同一个 `egui 0.36.2`，无冲突。

### 发现 5：`bevy_editor_pls` 已停更

最新 `0.10.0`，发布于 **2024-10-14**，约两年未更新。
它的定位是"给现有 Bevy 游戏挂一个运行时调试叠加层"，
而不是文档驱动的场景编辑器 —— 没有场景持久化、场景树编辑、资源管线。

**决定**：只作为参考实现阅读，不作为依赖。

读了官方 0.19 → 0.20 迁移指南，记录几条对本项目有影响的：

[workspace]

members = ["crates/scene_doc", "crates/editor_core", "crates/editor_ui", "crates/editor_app"]

`Cargo.toml` 里把"为什么钉在 egui 0.36"、"为什么不要
bevy-inspector-egui"写成注释，让后来者不必重新调查一遍。

**开发期编译优化**（Bevy 官方推荐做法）：

```toml
[profile.dev]

[profile.dev.package."*"]

```

第三方依赖（Bevy）在 dev 模式下也用 `opt-level = 2`，
编辑-运行循环的迭代速度明显提升。

在只有 stub 模块时就跑 `cargo fetch` 与 `cargo metadata`：

## 阶段 3：素材层 scene_doc

这一层刻意**不依赖 Bevy**。理由写在 `场景文档数据模型` 模块头部：
持久化格式必须独立于引擎类型，否则引擎换代就毁掉用户资产；
而且不依赖 Bevy 才能在没有 GPU、没有窗口的 CI 里完整测试。

### 决策：扁平实体表 vs 嵌套树

**问题**：场景直觉上是棵树，但编辑器里最常见的三种操作在嵌套结构上都是最坏情况：
拖放改层级要跨树搬移整个子树；重命名要定位并重建路径；
撤销要整份深拷贝两棵树做 diff。而且"按 ID 找实体"退化成 O(n) 遍历。

**决定**：扁平存储 + 父指针 + 顺序表（也就是 Godot 内部实际采用的思路）。

```text
entities: { 实体ID -> 场景实体 { 父实体: Option<实体ID>, 次序: u32, ... } }
tops:     [实体ID, ...]
```

**代价**：层级变成**隐式**的，必须靠 `校验()` 保证一致性。
这个代价是值得的：校验只需一次 O(n) 遍历，换来所有编辑操作都变成线性时间。

### 编译错误（第一轮）

第一次 `cargo check -p scene_doc` 报了 8 个错误，逐个记录根因：

| 错误 | 根因 | 修复 |
| --- | --- | --- |
| `PathBuf doesn't implement Display` ×3 | `thiserror` 的 `#[error("...{路径}...")]` 对 `PathBuf` 用默认格式化 | 改成 `{}", 路径.display()` |
| `cannot find type 组件工厂` | `lib.rs` 里 `pub use` 引用了不存在的类型（写文档时想当然） | 删掉 |
| `expected Option<实体标识>, found 实体标识` | 调用 `修正次序` 时漏了 `Some(...)` | 补上 |
| `type annotations needed` ×2 | `场景错误::非法("...".into())` —— `impl Into<String>` 参数多写了一次 `.into()`，编译器无法推断 | 去掉 `.into()` |
| `no method named 收拢 found for &mut 颜色值` | **方法名冲突**：`颜色值` 与 `属性值` 都有 `收拢`，在 `属性值::颜色(值) => 值.收拢()` 处产生歧义 | 把 `颜色值::收拢` 改名为 `收拢分量` |

**关于方法名冲突**这一条值得单独记：Rust 允许两个类型有同名方法，
但在模式匹配分支里 `值` 的类型推导可能无法选择正确的方法。
改名比加类型标注更清晰，也避免了后来者再踩。

### 测试失败（第一轮）

`cargo test -p scene_doc` 后 18 个集成测试里挂了 3 个：

**失败 1：`悬空父实体与次序冲突会被校验发现`**

```text
应当报告次序冲突，两者都要列出，
实际：文档校验报告 { 悬空父实体: [实体标识(9f70c135-...)], 次序冲突: [], ... }
```

**根因**：测试自身的逻辑错了 —— 我把实体 A 的父实体改成了不存在的幽灵，
A 就不再是顶层实体；同时又把实体 B 的次序改成 0。
两者不在同一个父分组下，自然不构成次序冲突。
**是测试写错了，不是校验器错了。**

**修复**：拆成两个独立的测试（`悬空父实体会被校验发现`、
`次序冲突会被校验发现`），每个只验证一件事。

顺带发现校验器里一个**真实缺陷**：分组键用了"是否出现在 `顶层顺序` 表里"
而不是"实际父实体是否为 `None`"，导致父实体为 `None` 但漏登记在
`顶层顺序` 里的实体会被错分成独立一组，既漏报它的次序冲突，
也无法与兄弟比对次序。已修正为按实际父实体分组。

**失败 2：`层级操作保持次序连续且不产生环`**

```text
assertion failed: 匹配循环错误(&文档.设为子实体(根, Some(根), 0))
```

**根因**：自环报的错误文案是"不能把实体设为自己的子实体"，
而测试的判定函数只匹配包含"循环"的错误。
**测试的判定条件太窄**，不是程序错了。

**修复**：把判定函数改名为 `匹配层级拒绝`，接受两种文案
（自环与后代环），并说明二者同属"必须拒绝的成环操作"。

**失败 3：`原文件损坏时可从备份恢复`**

```text
原文件损坏时应当能从备份恢复: 格式解析 { ... ExpectedDifferentStructName ... }
```

**根因**：这是**真实的实现缺陷**。`临时存储` 的读取逻辑先查原文件键，
一旦存在就直接 `解码`，**解析失败就把错误抛出去**，
永远走不到备份。而 `文件系统场景存储` 的实现是对的
（遍历候选、每个都完整解析成功才算数）。

**修复**：把 `临时存储::读取` 改成与生产实现同样的语义 ——
按 `原文件 → .bak → .tmp` 依次尝试，**每个候选都必须完整解析成功**。
只检查"文件是否存在"是不够的：一个存在但内容损坏的原文件
会让读取提前失败，从而永远用不上完好的备份。

**这条修复很有价值**：它同时让测试实现与生产实现的语义对齐，
否则测试通过也不能证明生产代码正确。

### 其他决策

**原子保存**：直接 `File::create(原文件)` 然后写入是危险的 ——
写到一半断电、磁盘满、进程被 kill，用户唯一的资产就变成半截内容。
采用三段式：

```text
1. 写 <场景>.tmp         内容不完整也只污染临时文件
2. 原文件改名 <场景>.bak   保留上一个完好版本
3. .tmp 改名到原文件       原子替换
成功后删 .bak；任一步失败则回滚
```

读取时按 `原文件 → .bak → .tmp` 尝试，覆盖"恰好崩溃在第 2、3 步之间"。

**`sync_all` 是必需的**：否则数据可能只在内核页缓存里，
断电后重命名成功但内容是空的。

**版本过新必须拒绝而不是尽力解析**：高版本可能引入了本版本不认识的
语义变更，强行解析会在保存时静默丢掉新版数据。

## 阶段 4：编辑器核心 editor_core

同样不依赖 Bevy。这一层的核心问题是**"修改"如何被表达**。

### 决策：全量快照 + 命令重放 vs 反向操作

**问题**：主流做法是给每个操作写 `undo()`，但下面这些操作的反向语义都不显然：

- 删除实体连同整棵子树 —— 反向要按原次序、原父实体精确复原
- 调整层级 —— 反向要复原新旧两侧的次序编号
- 拆除组件 —— 反向要复原组件的完整属性表

任何一处写错，表现就是"撤销之后场景悄悄坏掉"，很难定位。

**决定**：每次提交前把**变更前的整份文档**存进撤销条目。
撤销 = 换回快照；重做 = 重新应用命令。
正确性只依赖两件已有测试覆盖的事：文档能 `Clone`，命令能 `apply`。

**代价是内存**，因此引入字节预算（默认 64 MiB、256 步）：
超预算从最旧一端丢弃条目，只影响"能撤销多少步"，不影响撤销是否正确。

**保存点为什么用标记而不是下标**：若用下标，一旦因预算丢弃最旧条目，
所有下标都会位移，保存点就指向错误的条目 —— 表现为"存过盘的文件仍
显示未保存"，或更糟的"没存盘却显示已保存"。每个条目带一个只增不减的
标记，比较标记即可，丢弃条目不影响它。

### 决策：唯一修改入口

所有对文档的修改都必须经过 `编辑器状态::执行`，顺序不可交换：

```text
1. 克隆当前文档
2. 在克隆上应用命令
3. 失败则整体放弃，正本一字未动
4. 成功才提交回正本，并记录撤销条目
```

"在克隆上执行"是同时满足"命令可以部分执行后失败"和"失败不留痕迹"的关键。

### 编译错误

| 错误 | 根因 | 修复 |
| --- | --- | --- |
| `expected one of ->, where, or {` | 方法签名写成了 `) 场景结果<()> {`，漏了 `->` | 补上箭头 |
| `cannot find type 场景结果` / `no method 写入` | 上一条语法错误导致后面的代码未被解析，编译器报的"未使用导入"是**假警报**，我据此删掉了真需要的导入 | 把 `场景结果` 与 `场景存储`（trait 需在作用域内才能调用其方法）恢复 |
| 孤儿规则：`impl From<项目错误> for 场景错误` | 两个类型都是外部 crate 的，无法为它们写 `From` | 删掉这个 impl，改在调用点处理 |

**这里有个值得记的教训**：当一个语法错误让整段代码无法解析时，
编译器给出的"未使用导入"警告是不可信的。我照着警告删掉了
`use scene_doc::storage::场景存储`，结果语法修好后立刻报
`no method named 写入 found`。**先修语法错误，再看警告。**

### 测试失败（第二轮）

29 个集成测试里挂了 4 个：

**失败 1：`里程碑A_可以创建选择删除实体`**

```text
left: None
right: Some(实体标识(f3e3b981-...))
```

**定位**：加 `eprintln!` 打印实际状态。

```text
DEBUG 甲=实体标识(07251f01-...) 乙=实体标识(f3e3b981-...) 数量=0 全部=[] 主选中=None
```

**根因**：`编辑器状态::新建实体` 调用的是 `执行并记录`，
而**不是** `执行并选中`。前者只执行不选中，所以新建出来的实体
立刻失去选中状态 —— 用户点"添加节点"之后检查器没有任何反应。
这是**真实的功能缺陷**，测试正确抓到了它。

**修复**：改用 `执行并选中`，并加注释说明为什么必须用这个。

**失败 2：`里程碑B_撤销重做能精确还原属性修改`**

```text
left: 4
right: 3
```

**根因**：测试自身漏算了 —— `新建实体` 本身也占一步撤销，
所以总共是 1 + 3 = 4 步。**测试写错了。**

**修复**：调整断言，明确区分"新建占一步"与"三次改变换占三步"。

**失败 3：`资源移动会同步更新场景中的引用`**

```text
assertion failed: 状态.会话.文档.校验().无问题()
```

**根因**：**真实的实现缺陷**。`场景文档::改资源路径` 修改了资源表的键
与组件里的内嵌引用，但**没有重建资源表**，导致资源表里残留
"新路径已登记"与"组件引用已指向新路径"之间的不一致。

**修复**：在方法末尾调用 `同步资源表()`，并写清为什么必须重建。

**失败 4：`关闭项目后再打开能恢复场景内容`**

```text
left: "主场景"
right: "关卡"
```

**定位**：在 `打开项目` 里加调试输出。

```text
DEBUG 打开项目自动载入 "scenes/关卡.scene.ron" => Ok("ok")
DEBUG 启动场景清单=Some("scenes/关卡.scene.ron") 场景列表=["scenes/关卡.scene.ron"] 当前场景名=主场景
```

场景**确实加载成功了**，但场景名仍是"主场景"。

**根因**：**真实的设计缺陷**。场景文档的 `元数据.场景名` 一直没有
跟着保存路径走 —— `创建项目` 时自动建了一个叫"主场景"的空场景，
之后保存到 `scenes/关卡.scene.ron` 时**没有更新场景名**。
于是重新打开后，文档里的名字还是"主场景"。
这个现象很别扭：明明存成了"关卡"，打开却显示"主场景"。

**修复**：在 `保存场景到` 里，若当前场景名仍是占位名
（"未命名场景" / "主场景"），就用文件名作为场景名。
只认明确列出的占位名、不做模糊匹配 —— 用户真的把场景命名为
"主场景"是完全合理的，不能被静默改掉。

**失败 5（第二个测试文件）：`重做后实体必须回来`**

```text
DEBUG 重做=true 实体=实体标识(fc978bd3-...)
     存在=false
     文档实体=[实体标识(314ef5bb-...)]   ← 标识变了！
     可重做=3
     日志=["已重做：新建实体", "没有可撤销的操作", "已撤销：新建实体"]
```

**根因**：这是一个**我自己在设计时已经预见到、但实现时忘了接上的
严重问题**。`新建实体` 命令的 `指定标识` 首次执行时是 `None`，
UUID 由执行过程生成。重做时重新执行原始命令，就**又生成了一个
不同的 UUID** —— 结果是"撤销再重做之后，实体还在，但标识变了"。

后果极其隐蔽：所有记录了标识的外部状态（选择集、剪贴板、资源引用、
以及用户脚本里按标识查找实体的代码）都会静默失效。因为文档看起来
"有那个实体"，问题极难被发现。

**修复**（三步）：

1. 撤销条目新增 `新实体: Option<实体标识>` 字段；
2. `提交` 时把命令结果里的新实体标识存进去；
3. 重做时用 `重做用命令()` —— 它把首次生成的标识填回命令的
   `指定标识`，使重做成为**幂等**操作。

同时补了两个单元测试专门守住这条：
`重做命令会把首次生成的实体标识填回去` 与 `重做命令对其他命令保持原样`。

**这条修复是整个阶段最有价值的产出**：它把一个"几乎不可能被用户
说清楚、但会持续造成诡异 bug"的问题在测试阶段挡住了。

## 阶段 5：界面层 editor_ui

### 先查 API，再写代码

写界面前先读了 `egui_dock 0.21.1` 的源码，确认真实的 API 形状
（而不是凭对旧版本的记忆）：

```text
DockState::new(tabs) -> DockState<Tab>
Tree::split_left(parent: NodeIndex, fraction: f32, tabs: Vec<Tab>) -> [NodeIndex; 2]
Tree::split_below(...)
DockArea::new(&mut DockState<Tab>)
DockArea::show_inside(ui, &mut impl TabViewer)
TabViewer: id / title / ui / context_menu / on_close / closeable / allowed_in_windows
```

### egui 0.36 的面板 API 变动（踩到了）

按旧记忆写的代码报错：

```text
error[E0432]: unresolved import `egui::TopBottomPanel`
error[E0599]: no method named `style` found for reference `&egui::Context`
error[E0599]: no method named `set_style` found for reference `&egui::Context`
error[E0609]: no field `raw_scroll_delta` on type `&InputState`
error[E0609]: no field `space` on type `Modifiers`
```

**逐项查源码后的结论**：

| 旧 API（我的记忆） | egui 0.36 实际 | 说明 |
| --- | --- | --- |
| `TopBottomPanel` / `SidePanel` | **统一成 `egui::Panel`**（`Panel::top/bottom/left/right`） | 类型被合并 |
| `Panel::exact_height(f32)` | `exact_size(f32)` / `default_size(f32)` | 方法改名 |
| `Panel::show(ctx, ...)` | `show(ui: &mut Ui, ...)` | **不再接收 `&Context`**，而是接收父级 `&mut Ui` |
| `ctx.style()` / `ctx.set_style()` | `all_styles_mut()` / `set_style_of(theme, ...)` | 样式拆成亮色与暗色两份 |
| `input.raw_scroll_delta` | `input.smooth_scroll_delta` | 字段改名 |
| `modifiers.space` | 不存在。空格是**按键**，用 `input.key_down(Key::Space)` | 我把它误当成修饰键 |

**面板嵌套结构**（这个设计必须理解对才能写对）：

```text
根 Ui（覆盖整个视口）
 └─ CentralPanel
     ├─ Panel::top(菜单栏)     从父 Ui 扣除自身空间
     ├─ Panel::top(工具栏)     用剩下的空间
     ├─ Panel::bottom(状态栏)  用剩下的空间
     └─ DockArea              用最后剩下的空间
```

面板从父 `Ui` 里扣除自己占据的区域，父 `Ui` 的剩余区域才是下一个
面板可用的区域。因此**顺序会影响实际布局，不能随意调换**。

### 借用检查器的三轮搏斗

界面层最大的实现障碍不是 egui API，而是 Rust 的借用检查器。
`DockArea::new` 需要 `&mut 停靠布局`，而停靠布局在 `界面状态` 里，
同时查看器又要可变借用同一个结构体的其他字段。三个错误依次出现：

**错误 1：闭包对 `&mut` 的重复使用**

```text
error[E0501]: cannot borrow `*上下文` as mutable because
              previous closure requires unique access
```

即使 `CentralPanel::show` 的闭包只需要 `FnOnce`，闭包捕获的 `&mut`
也只能被使用一次，而闭包里要连续调用 4 次绘制方法。

**解法**：把整个绘制上下文临时搬进 `Option`，闭包里用 `take()`
一次性取得所有权。把"借用"变成"移出"，借用检查器就没得抱怨了。

**错误 2：结构体字段的双重可变借用**

```text
error[E0499]: cannot borrow `查看器` as mutable more than once at a time
```

**解法**：让查看器**拥有**绘制上下文（而不是借用），
这样可以在构造查看器**之前**先把停靠布局单独取出来交给 `DockArea`，
绘制结束后再放回去。

**错误 3：生命周期参数写成一个**

```text
error[E0261]: use of undeclared lifetime name `'platform`
error: lifetime may not live long enough
```

**根因**：把 `&'a mut 绘制上下文<'a>` 写成同一个生命周期，
会要求"引用本身"活得和"它指向的数据"一样久，
而这个引用只是函数内的局部变量。

**解法**：拆成两个生命周期参数：

```rust
struct 面板查看器<'借用, '数据> {
    上下文: &'借用 mut 绘制上下文<'数据>,
}
```

`'借用` 是持有这个引用本身的寿命，`'数据` 是上下文内部各字段
所指向数据的寿命。二者必须分开。

### 另一个借用问题：egui `Window::open` + 闭包

```text
error[E0499]: cannot borrow `打开` as mutable more than once at a time
```

`Window::open(&mut 打开)` 持有的可变借用会持续到 `show` 返回，
而窗口内容闭包又需要改它。

**解法**：用 `Rc<Cell<bool>>` 共享所有权，两处各拿一份。
同时把对话框拆成只借用 `界面状态` 的独立函数 ——
它不需要动作队列，"提出请求"与"执行请求"分开，
让对话框保持为可直接单测的纯输入组件。

### 顺手修掉的真实缺陷（clippy 发现的）

跑 clippy 时发现两处"两个分支完全相同"的 if/else，
说明**原本想做视觉区分但没写**：

- 场景树里"选中"与"未选中"用了**同一个颜色常量**，
  选中状态完全看不出来 → 改为选中使用强调色，与视口高亮一致
- Inspector 的字段标签同样有两个相同分支 → 既然提示统一由
  `格式提示` 组装，直接去掉分支

还有一处：资源路径改写里的三重循环 `break` 只跳出最内层，
会在同一实体上重复 `push` → 改用带标签的 `break '实体`。

界面逻辑（场景树摊平与过滤、资源树构建、菜单可用性判定、

## 阶段 6：Bevy 应用层 editor_app

### 决策：运行时住在独立的 `World` 里

**问题**：编辑器必须能把场景内容反映到游戏里，但需求明确要求
"运行时对实体、组件和资源的临时修改，不应自动写回编辑器文档"。

**决定**：把方向分清楚。

```text
场景文档  ──[构建世界]──►  独立的 Bevy World（运行时宿主持有）
    ▲                            │
    │                            │  只读地取统计数据
    └────── 绝不自动回写 ─────────┘
```

文档 → 世界只在"开始运行"时发生一次；世界 → 文档**默认不存在**。
停止运行时整个 `World` 被丢弃，运行时数据整体消失。

这样"运行时乱改不污染编辑器"不是靠约定或小心，而是靠
**数据被物理隔离** —— 两个世界，两份数据，中间只有一条单向通道。

### 编译错误

| 错误 | 根因 | 修复 |
| --- | --- | --- |
| `cannot find module crossbeam_channel` | `Cargo.toml` 漏加依赖 | 加入 `crossbeam-channel = "0.5"` |
| `expected due to this ... found signature defined here` | `属性值::浮点` 是**枚举变体**（构造函数），不是取值方法；应调用 `属性值::取浮点` | 改名 |
| `pattern binding 其他 is named the same as one of the variants` | `资源类别` 里正好有一个同名变体 `其他`，`其他 =>` 被解析成"绑定任意值到变量"，而不是"匹配该变体" | 改名为 `非图片类别` |
| `cannot borrow 编辑器 as immutable because it is also borrowed as mutable` | `编辑器.状态.选择.清理失效项(&编辑器.状态.会话.文档)` 同时可变与不可变借用同一结构体 | 改为先算出失效项再逐个移除 |
| `cannot borrow 界面 as mutable more than once` | 同一次调用里同时 `&mut 界面.状态` 与 `&mut 界面.动作` | 用结构体解构 `let UiStateHolder { 状态, 动作 } = &mut *界面;` |
| `WindowResolution: From<(f32, f32)> is not satisfied` | Bevy 0.20 改了 API | 改用 `WindowResolution::new(1600, 950)` |
| `this doc comment doesn't document anything` | 编辑时在文件末尾留下了一句孤立的文档注释 | 删掉 |

### 测试失败（第三轮，两个真实缺陷）

**失败 1：`未注册组件被跳过但不影响其他组件`**

```text
left: 2   right: 1
```

期望"跳过 1 个（未知组件）"，实际跳过 2 个。

**根因**：这是个**结构性的实现缺陷**。`可见性属性` 的
`实例化` 能成功（把属性写进那个擦除类型的实例），
但 `插入已知组件` 里**没有 `可见性属性` 的 downcast 分支** ——
我只写了 `downcast_ref::<Visibility>()`，而实际实例是编辑器自己的
包装类型。于是 `插入已知组件` 返回 `false`，被计入"跳过"。

这个缺陷的类型系统**抓不到**：`组件类型` 是类型擦除的，
注册表里加了类型、插入逻辑漏了分支，编译器不会有任何意见。
后果很隐蔽：注册表里有、属性也写进去了、运行时统计却把它算成"跳过"，
组件静默失效。

**修复**：

1. 在 `插入已知组件` 里补上 `可见性属性 → Visibility` 的映射
   （`true → Inherited`，`false → Hidden`，并在注释里写明这是**有损**映射，
   以及为什么选择有损而不是引入三态）；
2. **新增一个测试守住这条不变量** —— `注册表与插入分支一一对应`：
   遍历注册表里的每个类型，用声明的默认值走一遍真实的插入路径，
   断言必须成功。这一步比修 bug 本身更重要：它把一个
   "类型系统表达不了、只能靠人记得"的约束变成了自动化检查。

**失败 2：`运行时宿主启动停止后世界被彻底丢弃`**

```text
left: 4   right: 2
```

文档里只有 2 个实体，运行时世界却数出 4 个。

**定位**：打印世界里所有实体及其名字。

```text
DEBUG count_spawned=4 len=4
      实体列表=[(0v0, None), (1v0, None), (2v0, Some("甲")), (3v0, Some("乙"))]
```

**根因**：实体索引 0 与 1 **没有名字** —— 它们是 `World::new()`
本身创建的 2 个内部基础设施实体。我最初用
`entities().len()` 统计（它返回**曾经分配过**的索引数量，
实体被 despawn 后索引不回收，因此只增不减），
改成 `count_spawned()` 后仍然把内部实体算了进去。

**这是真实的统计缺陷**：诊断面板会显示"空场景也有 2 个实体"，
而且会让"场景里有 N 个实体，运行时就有 N 个"这条断言失去意义。

**修复**：`运行时实体数` 改为统计"带 `Name` 组件"的实体。
`构建世界` 会给**每一个**由场景文档创建出来的实体都插入 `Name`，
因此这个判据与"场景实体"的定义严格一致。

**顺带发现自己的测试有假断言**：原测试里写了一句

```rust
assert_ne!(宿主.运行时实体数(), 0.max(0));
```

`0.max(0)` 就是 `0`，所以这句等价于"实体数不等于 0" ——
一处毫无意义的自我安慰。改为断言 despawn 之后实体数**确实变成 0**，
这样"文档没被改动"的断言才有说服力：如果运行时根本没被改动，
"文档没变"是理所当然的。

**这条同样是个教训**：一个写错的断言可能长期存在而没人发现，
因为它总是通过。写隔离类测试时必须先证明"被隔离的那一侧真的变了"。

### 用真实的动作执行器做集成测试

核心层有自己的测试，但它们验证的是"API 能工作"。
为了验证**用户动作真的能走通整条链路**，写了
`crates/editor_app/tests/动作闭环.rs`：用 `World::run_system_once`
在无窗口、无 GPU 的环境里直接驱动**真实的系统函数**。

这条路多出三个真实的失败点：动作分派（match 分支是否接对了）、
上下文参数（`Local<拖动快照>`、`ResMut` 是否正确传递）、
资源变更可见性（系统改完后从外部读到的资源是否是新值）。

写完后立刻发现一个新的真实缺陷：

**失败 3：`通过动作队列可以新建实体并被自动选中`**

```text
left: None   right: Some(实体标识(902bff1c-...))
```

**根因**：与阶段 4 那个缺陷同源但在另一条路径上。
`执行动作队列` 里的 `UiAction::执行命令` 分支用的是 `执行并记录`，
不是 `执行并选中`。效果是：菜单里点"在场景树中新建实体"，
场景树多了一项，但检查器仍显示"未选中任何实体"，
用户必须再点一次才能编辑它。

**修复**：只对 `新建实体` 这一类命令走 `执行并选中`，
其余命令保持普通路径。加注释说明为什么不给所有命令都做选中 ——
删除一个东西之后自动选中别的东西会让用户困惑。

**这说明集成测试是有价值的**：同样的缺陷在两条不同路径上各出现一次，
只测其中一条会漏掉另一条。

## 事故记录：一次文件编码损坏

### 事情经过

修 `undo.rs` 的单元测试调用点时，我没有用编辑工具逐处修改，
而是用 PowerShell 做正则批量替换：

```powershell
(Get-Content file -Raw) -replace '...' | Set-Content file -NoNewline
```

结果：`Set-Content` 以**系统默认编码（GBK）**写回，
而文件里含大量中文。文件损坏，且 `-NoNewline` 还把行尾全部吃掉了。

**症状**：读文件报 `invalid UTF-8 text`；PowerShell 里显示为乱码
（`撤销与重做�?//!`）。

### 处理

1. 先确认损坏范围（`[System.IO.File]::ReadAllBytes` 看字节）；
2. 删掉损坏文件（删除前校验了绝对路径，确认是预期目标）；
3. **完整重写**该文件，并顺带把这一轮要做的修复一并写入；
4. 重写后用 `ReadAllBytes` 确认字节数与 UTF-8 有效性。

### 教训（已落实到后续操作）

- **不用 PowerShell 的文本替换去改含中文的源文件**。
  `Get-Content` / `Set-Content` 的默认编码在中文 Windows 上是 GBK，
  会破坏 UTF-8 内容。
- 若确实要用脚本改，必须显式指定编码：
  `[System.IO.File]::WriteAllText($f, $t, (New-Object System.Text.UTF8Encoding($false)))`
  （后续所有脚本化替换都改用了这个形式）。
- **编辑工具才是首选**。批量替换省下的时间远小于一次损坏的代价。
- 删除文件前先 `Resolve-Path` 并校验路径符合预期。

## 阶段：完整国际化（符号键 + 覆盖核对）

本轮唯一目标是把中英双语从"能切换"做到"机制正确、可自动查漏"，
不新增任何编辑器功能。

### 做了什么

| 事项 | 结果 |
| --- | --- |
| 翻译键 | 从"中文原文当键"改为**稳定的 ASCII 符号键** |
| 翻译入口 | 从 `editor_ui` 下沉到 `editor_core::i18n`（依赖是单向的，历史面板要显示命令名） |
| 词表 | 257 条，真相来源是 `crates/editor_core/i18n/messages.tsv` |
| 生成器 | `tools/gen_messages.py` 生成 Rust 词表，并核对中文覆盖 |
| 占位符 | 统一为位置参数 `{}`，配 `语言::填充(键, 参数)` 在运行时替换 |
| 关键区域清单 | 菜单栏、工具栏、面板标题、视口、场景树/检查器、语言自称 |

### 为什么键要改成符号键

旧写法 `语言.取("保存场景")` 有个隐患：**改中文措辞就等于换键**。
词表、调用点、测试要同时改，漏一处就静默查不到。
现在 257 条词条都是 `键 / 中文 / 英文` 三元组，
改措辞只动词表一行；键必须是规范小写 ASCII，
有测试挡住"顺手把中文当键"的回退。

### 缺失翻译的行为

`取` 查不到键时**返回键本身**，界面会直接显示 `menu_file_save_scene`。
比静默退回中文更好：退回中文会让人误以为已经翻好。
同时 `tools/gen_messages.py` 会扫描源码，**漏翻译时生成阶段就失败**。

### 本轮踩到并修掉的坑

1. **迁移脚本少吃掉一个右括号**：正则匹配 `语言.取("中文"` 时没包含
   原有的 `)`，替换后又补了一个，62 个调用点各多出一个 `)`，整个 crate 编译不过。
   教训：批量改代码要对**括号平衡**做一次机械校验，而不是只看替换计数。
2. **模板字面量被整体替换成键**：`format!("{}_改", 名称)` 变成 `format!("modified", 名称)`，
   占位符丢了。模板必须走 `填充`，不能整体换成键。
3. **生成器对三列一律 `strip`**：把"用前导空格做对齐"的文案改坏了，
   覆盖核对因此误报漏翻译。已改为只 `strip` 键。
4. **排版不是文案**：菜单勾选标记与前导空格原本写成了带中文的格式串，
   让"这一行有没有界面文案"难以判断。改成不含中文字面量的纯格式串。
5. **菜单定义以中文当键**：`菜单项动作(文本)` 与"文本 → 面板"反映射都按中文匹配，
   一旦界面换成英文，动作就派发不出去。改成按**键**匹配后与语言无关。
6. **面板名有两个真相来源**：四个面板各自定义了一份**无人调用**的 `标题()`。
   已删除，统一为 `Tab::标题(语言)` 与 `Tab::菜单键()`。

## 阶段：错误与日志国际化 —— 批次 0（检查器回归 + 跨行文案漏网）

### 修掉的回归：检查器的字段名与提示仍是中文

于是原样返回中文 —— 英文模式下检查器全是中文。

当时所有测试都是绿的：类型对、词表完整、调用点核对也通过
（因为字形上根本没有"调用"）。而我之所以没发现，
是因为**截图里检查器根本没显示**（它是需点击的标签页），
我却据此下了"检查器已覆盖"的结论。这是虚报，已在新文档里改正。

并用"把一条改回中文"反向验证过它们确实会失败。

### 新发现：扫描器看不见跨行字符串字面量

Rust 允许行尾反斜杠续行，于是一句文案可能横跨多行源码。
扫描器的字面量正则用了 `[^"\\\n]*`，**遇到换行就停**，
因此这类文案既没进词表、也没被任何检查发现。实际漏了 5 条：

* 关于窗口的"本版本已实现…"整段
* 历史面板的"游戏未在运行…"
* 历史面板的"运行时世界与编辑器文档是两份独立数据…"
* 历史面板的"本面板展示的是游戏运行时的 ECS 统计…"
* 性能面板的"游戏未运行，没有性能数据…"

改法：字面量正则改为 `(?:[^"\\]|\\.)*` 配 `re.S`，并把这段教训写进
`tools/gen_messages.py` 的注释。同时补上 8 条词条
（含 `属性值` 摘要的"空/{} 项/{} 个字段"）。

* `资源类别::显示名()` 改为 `词条键()`：`scene_doc` 不再承载用户文案，

## 阶段：错误与日志国际化 —— 批次 1（日志结构化 + Console 双语）

### 审计结论（先核实现状，未凭描述猜测）

* `日志条目 { 级别, 消息: String }` —— **没有时间戳、没有来源**，消息在调用点
  就被拼成最终字符串；Console 直接渲染它。共 **71 个调用点 / 66 条不同中文文案**。
* `日志级别::前缀()` 返回硬编码中文 `[信息]/[警告]/[错误]`，**并且会显示在 Console 每行前面**
  —— 这是一处此前没被发现的中文残留。
* Console 现有能力：级别勾选（带角标计数）、关键字搜索、清空、空状态、自动滚到底部、
  2000 条上限。**搜索是在渲染后的文本上做的**，这一点对新设计有约束。
* 依赖仍是单向的，没有 `editor_i18n` crate，词表在 `editor_core::i18n`。

### 设计：内容分两种，支持分批迁移

```rust
pub struct 日志条目 { pub 级别: 日志级别, pub 内容: 日志内容 }

pub enum 日志内容 {
    结构化 { 标识: &'static str, 参数: Vec<日志参数> },  // 稳定身份 + 结构化参数
    自由文本(String),                                    // 尚未迁移，保持原行为
}
pub enum 日志参数 { 用户数据(String), 诊断(String), 数值(i64) }
```

三个关键点：

1. **身份不是句子**：结构化条目存的是符号键（`log_scene_opened`），
   改中文措辞不影响身份，也不可能出现"英文句子当唯一标识"。
2. **渲染发生在显示时**：`条目.渲染(语言)`。因此**切换语言后缓存里的历史日志
   会跟着变成新语言**，不需要重新产生一条日志。这是本轮的核心要求。
3. **参数不翻译**：路径、实体名、场景名、资源名按语义以 `用户数据` 传入，
   模板翻译、参数原样填入。`自由文本` 变体让未迁移的 66 个调用点行为完全不变，
   从而支持分批迁移 —— 而不是为了"看起来干净"把日志删掉。

### 本批迁移的调用点（8 处，均可在实际运行中复现）

| 标识 | 位置 | 参数 |
| --- | --- | --- |
| `log_project_opened` | `editor_core/state.rs` 打开项目 | 项目名(用户数据) + 场景数 + 资源数 |
| `log_scene_opened` | 打开场景 | 路径(用户数据) |
| `log_scene_saved` | 保存场景 | 路径(用户数据) |
| `log_scene_created` | 新建场景 | 场景名(用户数据) |

| `log_scene_autoload_failed_hint` | 失败后的提示 | 无 |
| `log_language_changed` | 切换界面语言 | 语言自称(用户数据) |
| `log_level_info/warning/error` | Console 级别前缀 | 无 |

## 阶段：错误与日志国际化 —— 批次 2（scene_doc 错误结构化）

### 审计结论

`scene_doc` 共 3 个 thiserror 类型 / 15 个变体。其中**已经**带结构化字段与
`#[source]` 的有 5 个（文件读写 / 格式解析 / 版本过新 / 保存失败 / 路径非法 / 注册表
—— 路径、版本号、底层原因都在）。真正的问题是另两个：

* `结构非法(String)`、`编码失败(String)`：**把一整句中文当成错误身份**。
* 更普遍的问题不在字段，而在**没有稳定类别**：上层若要区分"是读取失败还是解析失败"，
  只能去比较 `Display` 的中文句子 —— 那等于把自然语言当身份，改文案就改行为。

### 设计（不替换字符串，而是加稳定身份）

```rust
pub enum 场景错误类别 { 文件读写, 格式解析, 结构非法, 版本过新,
                        路径非法, 编码失败, 保存失败, 注册表 }
pub enum 错误参数 { 路径(PathBuf), 数值(u32), 诊断(String) }

impl 场景错误 {
    pub fn 类别(&self) -> 场景错误类别;
    pub fn 消息键(&self) -> &'static str;      // ASCII 键，与语言无关
    pub fn 参数(&self) -> Vec<错误参数>;
    pub fn 本地化(&self, 键, 语言: &dyn Fn(&str) -> &'static str) -> String;
}
```

四个关键决定：

1. **类别是纯语义标签**：与语言无关，可安全用于匹配、测试与日志检索。
   身份不再来自句子。
2. **`scene_doc` 只输出键，不查表**：它不依赖界面层，也没有全局语言状态；
   `本地化` 的语言以**函数参数**传入（`&dyn Fn(&str) -> &'static str`），
   因此测试可以确定地指定语言，不会互相污染。
3. **底层原因以 `诊断` 参数保留**：第三方错误文本不可翻译，
   但必须留着 —— 强行塞进翻译占位符只会毁掉诊断信息。
   `#[source]` 与 `std::error::Error::source()` 未动。
4. **不做破坏性重构**：`Display` 与全部既有变体、字段、`#[from]` 保持原样，
   只**新增**类别与参数访问器。因此 `?` 传播与现有调用点无需改动。

### 上层接入：嵌套可翻译参数

批次 1 的日志参数只能填字符串，先把内层错误渲染成字符串会把它**固化在生成时的语言**。
本批给 `日志参数` 加了可递归的子消息：

```rust
日志参数::子消息 { 标识: &'static str, 参数: Vec<日志参数> }
日志参数::从场景错误(&场景错误)   // 键 + 参数，不渲染
```

`日志条目::渲染` 改为自己走占位符（不再借 `语言::填充`，因为 `&dyn Display` 拿不到语言），
把语言一路传进嵌套层 —— 于是**外层与内层一起**按当前语言渲染。

`log_scene_autoload_failed` 因此从"路径 + 整句诊断"改为"一个结构化错误参数"。

## 修复：停靠布局只显示两个面板（根因：fraction 归属搞反）

### 现象

默认布局序列化出来有 4 个叶子、8 个标签，但 GUI 里只有左侧场景树和中央视口，
Inspector / 历史 / 运行时 ECS / 性能 / 资源浏览器 / 控制台全部不出现，
底部状态栏也不见。连续四个批次因此被迫"临时改生产布局"才能验收面板。

### 排查中排除掉的（都有实验证据）

| 假设 | 结论 |
| --- | --- |
| 面板注册 / 标签映射错 | 排除。8 个标签落在 4 个互不相同的叶子节点上 |
| 反复用 `NodeIndex::root()` 把树建错 | 排除。序列化树结构与预期一致（0.74 / 0.72 / 0.22 三个分立节点都在）|
| 视口用绝对矩形侵占空间 | 排除。`内容矩形 = ui.available_rect_before_wrap()`，来自叶子自己的 Ui |
| `hidable_tab_bars` / `show_leaf_collapse_buttons` | 排除。实验 B 关掉后故障不变 |
| 底部状态栏把可用矩形算坏 | 排除。实验 C 整个移除状态栏后故障不变 |

### 真实根因

**`egui_dock 0.21.1` 的 `fraction` 给的是"新节点"的比例，而不是旧节点的。**

原代码按相反理解写的：

```rust
// 右侧：检查器等，占 26% 宽度
split_right(NodeIndex::root(), 0.74, vec![检查器, …])   // 以为 0.74 = 旧节点(主区)占 74%
```

而在本版本里 0.74 是**右列自己**的宽度。于是：

* 右列拿到 74% 宽，底部拿到 72% 高；
* 两个巨大的区域把左列和中央区挤成很窄的条，看起来就像"只有两个面板"。

**这一点是实测确认的，不是读注释推出来的**：把 `split_left` 的分母从 0.22 改成 0.78 并截图，
场景树宽度真的从 ~25% 变成 ~86% —— 说明 fraction 直接作用于新节点。
egui_dock 的文档注释写的是"the old node will attempt to occupy"，
与本版本实际行为相反，**以实测为准**。

### 修复

`crates/editor_ui/src/docks.rs::默认布局()`：

* 三次 split 都改用**上一次 split 的返回值**，不再反复写 `NodeIndex::root()`
  （它恒等于 `NodeIndex(0)`，虽然本版本能复用索引 0，但依赖这一点是脆弱的）；
* 比例改成期望的**新节点**占比：右列 `0.26`、底部 `0.28`、场景树 `0.22`；
* 顺序调整为"先切右列 → 再在主区切底部 → 最后在上方切场景树"，
  使底部横跨左+中两列（与 Godot 一致）；
* 在函数上方写明最终布局树、方向与两条必须记住的 egui_dock 语义
  （fraction 给新节点；返回值是 `[旧, 新]`），并注明**不要照抄文档注释**。

### 实际 GUI 验证（真实运行截图）

英文模式、默认布局、窗口 1615x987：

* 左：Scene Tree（~22%）
* 中：Viewport（~22%）
* 右：**Inspector / History / Runtime ECS / Performance**（~26%）

## 关键结论：截图管线不可信，改用进程内叶子矩形作为依据

### 冲突的证据

- 用户亲自运行应用，观察到**各面板均存在**。
- 我的 `抓图.ps1` 在 `split_right = 0.74` 下反复只截到「场景树 + 视口」两块。
- 同一份 `0.74` 代码，进程**自己**通过 `BEVY_STUDIO_DUMP_LEAF_RECTS`
  报告的四个叶子矩形是：
  ```
  场景树    x   6.0..  254.0   w= 248.0
  视口      x 266.7.. 1177.3   w= 910.7
  检查器    x 1190.7..1594.0   w= 403.3   y 89.3..925.3
  资源浏览器 x   6.0.. 1177.3   w=1171.3
  ```
  也就是说布局**是对的**：左 15% / 中 55% / 右 25%，底部横跨左+中。

### 判定

用户观察 + 进程内矩形互相一致，截图与两者都矛盾。已排查并排除：

- 抓图脚本的窗口选择：`抓图.ps1` 第 79 行用 `(Get-Process -Id $进程.Id).MainWindowHandle`，
  取的是自己启动的 PID 的主窗口，不是别的进程。
- 等待时长：默认已是 16 秒；显式传 15 秒重跑，结果不变。
- 时间不够导致布局未稳定：排除。

因此结论是 **`PrintWindow(PW_RENDERFULLCONTENT)` 对这个 Bevy/wgpu 窗口
返回的不是真实合成画面**（对该类硬件加速交换链，PrintWindow 常返回不完整帧）。
此后**不再用该截图判断面板可见性**。

### 本轮改动

- `crates/editor_ui/src/docks.rs`：`split_right` `0.26 → 0.74`。
  依据是进程内实测的四个叶子矩形（见上），以及 `egui_dock` 的
  `fraction` = 旧节点保留比例这一已标定语义。
- 预期效果：检查器列从 1171px（73%）降到 403px（25%），视口从 228px 升到 911px。

## 1. GUI 采集与自动验收

### 1.1 旧做法为什么必须废弃

上一轮已经确认：`PrintWindow(PW_RENDERFULLCONTENT)` 对 Bevy/wgpu 窗口返回的不是
真实合成画面（曾出现"只截到两块面板"而进程内几何显示四块俱全）。基于错误截图去改
生产代码，比不截图更有害。

### 1.2 采用的方案：进程内渲染目标回读

新增 `crates/editor_app/src/capture.rs`：

- 用 Bevy 的 `Screenshot::primary_window()` 从**渲染目标**回读这一帧的窗口画面
  （`wgpu` buffer readback，不经 GDI、不依赖窗口是否被遮挡）；
- **同一帧**把布局证据写成 JSON：语言、主题、UI 缩放、窗口尺寸、
  每块区域的真实矩形、状态栏文案、可见面板键、工作区 id；
- 由 `gui_probe` 离线判定，应用自身**不做任何判定**，避免"自证清白"。

关于 Windows Graphics Capture：它能拿到同样的合成结果，但需要 WinRT 帧池 +
D3D11 互操作 + 异步等待，代码量与权限面都更大；而进程内回读读的正是
**同一份交换链内容**，且天然与布局证据同帧。因此本轮采用后者，
WGC 作为"未来若需要抓取他人窗口"的备选记录在此。

### 1.3 验收工具 `crates/gui_probe`

| 能力 | 实现 |
| --- | --- |
| 确认目标进程与窗口 | Win32 `EnumWindows` + 进程号匹配，取标题/类名/客户区/DPI；启动时声明 per-monitor DPI 感知，否则 150% 缩放下客户区会被虚拟化成 1/1.5 |
| 获取真实画面 | 读应用写出的 PNG（渲染目标回读） |
| 检测面板与状态栏可见性 | 证据里的区域矩形 + 像素统计（唯一色数、主导色占比、对比像素数） |
| 自动检查 | 20+ 条断言：尺寸一致、画面非常量、主题背景吻合、每区域有内容、菜单/工具栏/状态栏有文字像素、布局关系、视口占比、语言与文案 |
| 保存证据 | `PNG + 证据 JSON + report.json + report.md + 应用日志` |
| 区分失败类型 | 退出码 3 = 采集失败（文件缺失/尺寸不符/窗口未确认），2 = 界面缺陷（证据齐全但断言不成立） |

**这个区分本轮立刻发挥了作用**：第一次运行时报告"采集失败"，
进一步看是 150% 缩放下 `GetClientRect` 返回逻辑像素（DPI 虚拟化）——
是工具的问题，不是界面的问题；修好工具后同一份界面代码判为通过。

### 1.4 顺手抓到的真实缺陷：底部占了 72%

`egui_dock 0.21` 的 `fraction` 语义按源码确认是**第一个子节点**的比例：

| 调用 | 第一个子节点 | 效果 |
| --- | --- | --- |
| `split_right` | 旧（左） | 比例越大左侧越宽 |
| `split_below` | 旧（上） | 比例越大上方越高 |
| `split_left` | 新（左） | 比例越大左侧（新）越宽 |

上一轮把 `split_right` 从 0.26 改成 0.74 修好了右列，但同一份布局里
`split_below(0.28)` 的实际含义是"上方 28%"，于是**底部占 72%、视口被压成窄带**。
这个缺陷在旧截图里看不出来，在进程内截图里一眼可见。已改为 0.72，
并补上按真实占比断言的几何测试（`默认布局各栏占比合理`，覆盖 1200×800 与 1024×700）。

## 2. 命名工作区

### 2.1 数据模型

`crates/editor_ui/src/workspaces.rs`：

- `工作区 { id, 名称, 内置, 布局(RON 文本), 基线布局, 布局版本 }`
- `工作区集 { 项, 当前, 当前布局(活对象), 备注 }`

布局存**文本**而不是嵌套结构，是为了让**单个**工作区解析失败只回退它自己，
而不是让整份配置失效（测试 `单个工作区布局损坏只影响它自己` 固定该行为）。
当前布局保持为活对象：`DockArea` 每帧要可变借用它，若每帧反序列化不可接受。

### 2.2 四个内置预设（结构性不同，不是换名字）

| 工作区 | 结构 | 用途 |
| --- | --- | --- |
| 通用 | 右列 26% + 底部 28% + 左列 22% | 首次启动的默认 |
| 场景 | 右列 24% + 底部 18% + 左列 20%，资源折叠进左列标签组 | 视口优先 |
| 资源 | 资源浏览器占中央整列（726×816），视口移到右上，检查器在其下方 | 资源浏览 |
| 调试 | 底部 45%（控制台/运行时 ECS/资源），右列性能/历史/检查器 | 排查问题 |

四个预设都包含全部 8 个面板与视口；关闭的面板可从「窗口」菜单或工具栏图标重新打开
（测试 `关闭面板后仍可通过聚焦重新访问`）。

### 2.3 生命周期与迁移

- 新建 / 复制 / 重命名 / 删除（内置受保护）/ 重置当前 / 重置全部内置；
- 切走时先**同步活布局**回记录，避免丢改动；重置只影响当前工作区；
- 存档格式版本 2；旧版单布局（版本 1）迁移成名为「迁移的布局」的用户工作区；
- 缺失的内置工作区会被补回；未知字段被忽略；坏布局回退基线或内置预设。

### 2.4 界面

顶部新增 26px 工作区栏：左侧身份图标 + 工作区标签（当前项带强调描边），
右侧固定动作组（新建/复制/重命名/删除/重置/更多）。
**动作组先占位**，窗口变窄时被挤压的是标签而不是按钮，不会出现"窗口一小就切不了工作区"。
长名称截断到 14 字符并保留完整悬停提示。窗口菜单里也有同源的工作区入口并打勾。

## 3. 主题系统

### 3.1 语义配色

`crates/editor_ui/src/theme.rs` 定义 33 个**语义槽位**
（窗口/面板/输入框/悬停/激活背景，主/次/禁用/链接文字，强调/强调亮/选中，
边框/强边框，视口/网格/坐标轴/实体框/选择框，信息/成功/警告/错误，
按钮三态，标签栏/激活标签/标签文字/分割线/浮窗标题/提示背景）。

面板代码只允许取槽位，不写字面色值 —— 这是"所有面板看起来属于同一个编辑器"的前提，
也是主题切换不会出现"某个面板忘了换色"的原因。

### 3.2 三个内置主题 + 用户主题

| 主题 | 特征 | 实测截图平均亮度 |
| --- | --- | --- |
| 深色 dark | 中性灰 + 蓝强调 | 30.9 |
| 浅色 light | 白底深字 | 242.2 |
| 高对比度 high_contrast | 纯黑底 + 纯白字 + 黄强调，字号 14 | 14.5 |

用户可新建、另存为、重命名（改主题名）、删除；内置主题被编辑时写入**覆盖层**，
出厂定义永远保留，可一键恢复；导入的主题一律变成用户主题（防止外部文件伪装内置）。

### 3.3 主题编辑器与实时预览

`theme_editor.rs`：32 个颜色槽位按 8 组表驱动渲染（加一个颜色 = 表里一行 + 词表一条），
5 个外观滑块（UI 缩放 / 基础字号 / 圆角 / 间距 / 图标大小）。
改动写入**草稿**，绘制每帧优先使用草稿 → 改一个颜色下一帧整界面就变；
关闭窗口即丢弃草稿，界面自动回到主题库当前主题；保存才写回主题库。

外观参数在应用与加载时都会被 `外观::收敛()` 夹到安全区间
（缩放 0.7~2.0、字号 9~22、圆角 0~12、间距 2~16、图标 12~32），
避免一份手改的配置把界面压成一条线、连"重置"都点不到。

### 3.4 持久化

`编辑器配置.主题` 存主题库 RON，与 `工作区`、`布局`、`偏好` 完全独立的字段。
主题存档损坏只回退主题，工作区与语言不受影响（测试 `损坏的主题存档回退内置且不影响工作区`）。
环境变量 `BEVY_STUDIO_THEME` 可指定启动主题，供验收使用。

## 4. 开源图标资产

### 4.1 选择与核实

| 项目 | 内容 |
| --- | --- |
| 来源 | [tabler/tabler-icons](https://github.com/tabler/tabler-icons) |
| 版本 | `v3.49.0`（GitHub Releases API 查到的 latest，2026-10-05 发布） |
| 许可证 | MIT（`crates/editor_ui/assets/icons/LICENSE`，Copyright (c) 2020-2026 Paweł Kuna） |
| 下载方式 | 逐文件从 `raw.githubusercontent.com/.../v3.49.0/icons/outline/<name>.svg` 取原始 SVG，共 48 个 |
| 本地来源记录 | `crates/editor_ui/assets/icons/README.md` |

比较过 Kenney UI Pack（PNG，CC0）与 Lucide（ISC）：Kenney 是位图且风格偏游戏化，
Lucide 与本项目需要的"细线描边编辑器图标"接近但 Tabler 的图标覆盖面更全
（`adjustments-horizontal`、`chart-histogram`、`device-desktop-analytics` 等直接可用）。
最终选 Tabler。

### 4.2 集成方式：构建期烘焙 + 编译期内嵌 + 运行时染色

- 运行时**不引入任何 SVG 解析依赖**。`tools/icon_bake`（构建期工具，resvg 0.45）
  把 SVG 烘焙成 32×32 PNG（逻辑 16px × 2 倍 DPI），描边统一替换为白色；
- `cargo run -p icon_bake -- --check` 校验 PNG 齐全且尺寸正确；
- `crates/editor_ui/src/icons.rs` 用 `include_bytes!` 把 48 个 PNG 编进二进制
  （合计 41 KB），首次使用时解码并上传为 egui 纹理并缓存；
- 运行时用 `Image::tint(主题色)` 染色：**一套文件覆盖深色/浅色/高对比度**；
- 缺失资源会退回文字按钮并给出"图标资源缺失"提示，不会静默消失。

对比过的替代方案：运行时用 resvg 渲染（多约 30 个传递依赖、每次启动解析 SVG、
发布包变大）与引入 egui_extras 图片加载器（仍需解码器且路径依赖）。
烘焙 + 内嵌的运行时依赖为 0，且干净构建与发布构建加载路径完全一致。

### 4.3 实际使用位置

- 工具栏：运行/暂停/单步/停止、撤销/重做、保存、新建/删除实体、6 个面板快捷入口、主题编辑器；
- 工作区栏：工作区身份图标 + 新建/复制/重命名/删除/重置；
- 状态栏：保存状态（成功=绿勾 / 未保存=软盘+警告色）；
- 主题编辑器：每个主题的类型图标（月亮/太阳/对比度/自定义）。

## 5. 设计系统与界面一致性

- `主题::应用` 一次性设置两份 egui 样式（亮/暗），包括控件四态

## 8. 已知限制（如实记录）

1. **独立原生窗口**：`bevy_egui 0.43` 不处理 `egui::ViewportCommand::CreateWindow`
   （已在源码中确认：没有 viewport 命令分发），因此"把面板拖成真正的操作系统窗口"
   在当前依赖下无法实现。本轮实现的是 `egui_dock` 的浮窗表面（可拖动、可停靠回来、
   可持久化），并在文档中明确区分二者，没有把它说成原生窗口。
2. **菜单项图标**：egui 的菜单项是纯文本渲染，加图标需要自定义条目绘制。
   本轮把图标用在了工具栏、工作区栏、状态栏与主题编辑器；菜单仍靠文字与勾选。
3. **PrintWindow 对比未在本轮复现**：`抓图.ps1` 已在接手前的提交里删除，
   本轮没有重建外部抓图对比；"PrintWindow 不可信"的结论沿用上一轮记录，
   本轮新增的是"进程内回读与操作系统客户区尺寸一致"的正向证据。
4. **浅色主题下视口顶部叠加条**的对比度偏低（深色半透明底 + 次要文字色），
   已记录待下一轮把叠加条改为随主题切换的显式底色。
