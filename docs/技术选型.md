### 2.2 关键发现一：`egui` 不能用最新版

`egui` 最新是 **0.37.0**，但**不能**直接用。查依赖要求：

- `bevy_egui 0.43.1` 依赖 `egui ^0.36`
- `egui_dock 0.21.1` 依赖 `egui ^0.36`

若在 `Cargo.toml` 里写 `egui = "0.37"`，会和这两个库要的 `egui 0.36`
**同时存在**，导致 `egui::Ui`、`egui::Context` 在类型上是两个不同的类型，
编译期报一堆看似莫名其妙的类型不匹配错误。

**本项目的做法**：显式钉在 `egui = "0.36"`，并在 `Cargo.toml` 与
`技术选型.md` 里都写明原因。验证方式是读 `Cargo.lock`：

```text
name = "egui"        version = "0.36.2"   ← 只有这一个版本
name = "bevy_egui"   version = "0.43.1"
name = "egui_dock"   version = "0.21.1"
```

`cargo tree -i egui` 显示三方都收敛到同一个 `egui v0.36.2`，无冲突。

### 2.3 关键发现二：`bevy-inspector-egui` 与 Bevy 0.20 不兼容

这是本次调查里最重要的否决结论。`bevy-inspector-egui 0.37.0` 的依赖：

```text
bevy_app    ^0.19.0
bevy_ecs    ^0.19.0
bevy_reflect ^0.19.0
bevy_egui   ^0.40.0
egui        ^0.34
```

它针对 **Bevy 0.19 + egui 0.34**。而 `bevy_egui 0.43.1` 要 `egui 0.36`、
Bevy 0.20。若硬要引入，会同时把 Bevy 0.19 与 0.20、egui 0.34 与 0.36
拖进依赖图 —— 而 Bevy 的各个子 crate 之间靠类型严格耦合，
两个大版本共存意味着 `bevy::prelude::Transform` 与
`bevy_inspector_egui` 看到的 `Transform` 是不同类型，**根本无法互操作**。

**结论：本项目自行实现 Inspector，不引入 `bevy-inspector-egui`。**

### 2.4 关键发现三：`bevy_editor_pls` 已不适合作为基础

`bevy_editor_pls` 最新版本停在 0.10.0（2024-10），约两年未更新，
对应的是很旧的 Bevy 版本。它作为"给现有 Bevy 游戏挂一个调试面板"的工具
仍然有价值，但**不适合**作为"面向日常游戏开发的完整可视化编辑器"的基础：
它的定位是运行时调试叠加层，而不是文档驱动的场景编辑器，
没有场景持久化、场景树编辑、资源管线这些本项目需要的核心能力。

**结论：仅作为参考实现阅读，不作为依赖。**

## 三、最终依赖清单与理由

### 3.1 直接依赖

| crate | 版本 | 为什么选它 | 考虑过的替代方案 |
| --- | --- | --- | --- |
| `bevy` | 0.20.0 | 目标引擎本体。选当前稳定版而非 git 版本，保证可复现构建 | 跟 `main` 分支：API 每天变，编辑器无法稳定开发 |
| `bevy_egui` | 0.43.1 | Bevy 与 egui 的官方级桥接，支持把 egui 绘制叠加在 Bevy 渲染之上 | 自己写 `bevy_ui` 界面：工作量巨大且 `bevy_ui` 缺少停靠、表格、树控件 |
| `egui` | 0.36 | 即时模式 GUI，迭代速度快，适合工具类界面；且是 `bevy_egui`/`egui_dock` 共同要求的版本 | `iced`（保留模式，但无停靠布局且与 Bevy 桥接不成熟）、`bevy_ui`（缺控件） |
| `egui_dock` | 0.21.1 | 提供可停靠、可拖动、可关闭、可浮动的面板布局，是"Godot 风格布局"的直接实现 | 手写面板布局：无法实现拖拽停靠，而这是明确需求 |
| `serde` + `ron` | 1.0.229 / 0.12.2 | 场景格式需要人可读、可进 Git、支持注释。RON 是 Bevy 生态的原生格式，社区熟悉 | JSON（无注释、无元组）、TOML（不适合深层嵌套）、bincode（不可读，无法做 diff 评审） |
| `uuid` | 1.28.0 | 实体与资源的稳定身份 | 自增整数（删除中间项后整体位移，会错位）、字符串 ID（易碰撞、占空间） |
| `rfd` | 0.17.2 | 跨平台原生文件 / 目录对话框 | `native-dialog`（同类，`rfd` 更活跃）、自己写（各平台差异大） |
| `crossbeam-channel` | 0.5 | 把阻塞的文件对话框丢到后台线程，结果回传主线程 | `std::sync::mpsc`（`Sender` 非 `Sync`，放进 Bevy 资源不方便） |
| `image` | 0.25.10 | 读图片真实像素尺寸，从资源创建精灵时填入正确包围盒 | 只依赖 Bevy 的 `Image`（需要资源服务器，编辑器侧不方便） |
| `opener` | 0.8 | 在系统文件管理器中定位资源 | 手写 `explorer.exe` 调用（不可移植） |
| `notify` | 8.2.0 | 资源变更检测（**已声明但本版本尚未接入**） | 轮询（简单但浪费 IO） |

### 3.2 关于 `image` 的特性裁剪

```toml
image = { version = "0.25.10", default-features = false, features = [
    "png", "jpeg", "webp", "bmp", "gif",
] }
```

Bevy 自己也会依赖 `image`。Cargo 会对同一 crate 的特性做**并集**，
因此这里的裁剪不会削弱 Bevy 的能力，只是避免本项目自己额外拖入
`tiff`、`hdr`、`dds` 等用不到的编解码器。

## 四、GUI 框架的详细对比

选 `egui` + `egui_dock` 是本次选型里最需要论证的一步，因为
"用 Bevy 做编辑器"最容易走错的弯路就是选错 UI 技术路线。

| 方案 | 优点 | 为什么没选 |
| --- | --- | --- |
| **egui + bevy_egui**（选用） | 即时模式，改一处立刻看到效果；控件齐全（树、表格、拖拽数值、颜色选择器、停靠）；与 Bevy 桥接成熟；`egui_dock` 直接给出可停靠布局 | 即时模式每帧重建 UI，超大列表需要虚拟滚动（`ScrollArea` 已支持） |
| `bevy_ui` | Bevy 原生，无额外依赖 | 它是**游戏内 UI** 框架，不是编辑器框架：没有树控件、没有属性表格、没有停靠、没有文本输入框（本版本 `EditableText` 才刚分离出来）。用它会陷入"先写一个 UI 框架" |
| `iced` | 保留模式、类型安全、架构清晰 | 与 Bevy 的集成不如 `bevy_egui` 成熟；无官方停靠布局方案 |
| `tauri` / Electron 前端 | Web 技术栈，控件生态丰富 | 引入第二种语言与运行时；编辑器需要直接访问 Bevy 的反射与 ECS，跨进程边界代价高 |
| 自绘（`wgpu` + 自己的 UI） | 完全可控 | 光是文本排版、输入法、剪贴板、无障碍就要数月，与"做出可用于开发的编辑器"的目标背道而驰 |

## 五、被否决的其他方案

### 5.1 不直接序列化 Rust 结构体作为场景格式

**诱惑**：`#[derive(Serialize)]` 打在 `Sprite`、`Transform` 上，直接存。
**否决理由**：

1. Bevy 的组件里有 `Handle<Image>` 这类运行时句柄，序列化它没有意义；
2. 引擎升级会改变字段名与结构，用户场景**全部失效**；
3. 编辑器专有元数据（展开状态、锁定）会被混进游戏数据；
4. 未知组件无法保留，"新版编辑器打开旧场景再保存"会静默丢数据。

**采用**：独立的弱类型属性模型（`属性值`）+ 组件注册表做双向转换。
格式与引擎类型解耦，代价是每个组件写一次转换。

### 5.2 不使用 `bevy_reflect` 作为 Inspector 的唯一驱动

`bevy_reflect` 很强，但**覆盖不到**编辑器需要的全部类型：
`Color`、`Handle<T>`、`Sprite` 里的枚举、以及游戏自己的组件都需要额外注册。
如果 Inspector 依赖反射，"某组件能不能编辑"就取决于它是否恰好派生了
`Reflect`，编辑器对没派生的类型毫无办法。

**采用**：注册表驱动 Inspector；`bevy_reflect` 留给 ECS 调试器
（只读浏览运行时世界，那里不需要写回文档）。

### 5.3 不把游戏内容塞进编辑器的主世界

如果把运行时实体直接生成在编辑器主世界里，那么"停止运行"就必须
逐个清理，一旦漏掉就会留下幽灵实体；而且游戏逻辑会直接改到编辑器
正在显示的数据。

**采用**：运行时住在**独立的 `World`** 里。停止时整个 `World` 置空，
运行时数据整体消失。隔离靠**两份数据**而不是靠清理逻辑写对。

### 5.4 不用 `.scene.ron` 以外的自定义二进制格式

**否决**：二进制更快更小，但场景文件需要进 Git、需要代码评审、
需要用户能在编辑器打不开时手工抢修。可读性优先于体积。

## 六、版本升级策略

| 升级对象 | 风险 | 应对 |
| --- | --- | --- |
| Bevy 小版本 | 中：迁移指南通常完整，但总有 API 改名 | 跟随官方迁移指南逐项核对；`scene_bridge` 是唯一直接接触 Bevy 组件的模块，改动集中 |
| Bevy 大版本 | 高 | 场景格式**不受影响**（这是分层的目的）；组件注册表里的转换函数需要跟着改；升级前先跑 `cargo test --workspace` 建立基线 |
| `egui` / `egui_dock` | 中高 | 已实测过一次版本陷阱（见 2.2）；升级时必须同时检查 `bevy_egui`、`egui_dock` 的 `egui` 要求是否对齐，并确认 `Cargo.lock` 里只有一个 `egui` |
| 场景格式版本 | 低（自己控制） | 加字段不升版本（靠 `serde(default)` 兼容）；改语义才升版本并写升级函数；读到更高版本直接拒绝加载 |

**升级前必做的三件事**：

1. `cargo test --workspace` 记录基线（应为 156 项全绿）；
2. `cargo tree -i egui` 确认没有出现两个 `egui` 版本；
3. `cargo clippy --workspace --all-targets` 确认零警告。
