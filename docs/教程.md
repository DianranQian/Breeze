## 第 0 步：先侦察，别急着写代码

### ① 要做什么

需求给了一大段功能清单。第一反应可能是"开始写界面"。
但**先花时间搞清楚环境和约束**，能避免后面大量的返工。

### ② 原理：约束优先于设计

软件设计里有一个常见误区：把"用户想要什么"当成唯一输入。
实际上同等重要的还有**"环境允许什么"**：

- 引擎版本决定了哪些 API 存在；
- 依赖生态决定了哪些现成能力可用；
- 工具链决定了能否构建。

这些约束如果事后才发现，可能推翻整个设计。

### ③ 侦察了什么

```powershell
pwd; Get-ChildItem -Force          # 目录是空的
git status                         # 不是 git 仓库
rustc --version                    # 1.99.0
rustup show                        # x86_64-pc-windows-msvc
```

### ⑧ 第一个坑：`link.exe` 找不到

```powershell
where.exe link.exe    # INFO: Could not find files for the given pattern(s).
```

**看起来**是 MSVC 环境缺失。**但不要下结论**，做实验：

```powershell
# 建一个最小程序
cargo run --manifest-path .probe/Cargo.toml
# → probe ok
```

**结论**：`cargo` 通过 Windows 注册表发现 Visual Studio 并自己配置链接环境，
`link.exe` 不需要在 `PATH` 里。

**经验**：`where.exe` 找不到 ≠ 环境缺失。工具链发现问题要用
**最小复现实验**验证，而不是读环境变量猜。

### 顺带发现的约束

最小程序的可执行文件落在了：

```text
C:/Spaces/Share/10_Code/10_Bevy/_build/target\debug\probe.exe
```

查上级目录发现 `.cargo\config.toml` 把 `target-dir` 重定向了。
**这是好事**（Bevy 整个空间只编译一次），
但意味着 `cargo clean` 会清掉整个空间的缓存 —— 必须写进 README。

## 第 1 步：核实依赖，两次关键否决

### ② 原理：依赖版本冲突为什么致命

在 Rust 里，**同名 crate 的不同大版本可以共存**，
它们是**不同类型系统里的不同类型**。

对普通库来说这通常只是体积问题。但对 Bevy 这种
"组件之间靠类型严格耦合"的引擎，后果是灾难性的：

```rust
// 你以为在传 bevy 0.20 的 Transform
// 实际编辑器看到的是 bevy 0.19 的 Transform
fn 设置位置(变换: &mut Transform) { ... }
// error: expected `Transform`, found `Transform`   ← 看起来像编译器出错了
```

### ③ 查了什么

**不凭记忆，直接查 crates.io API**：

```powershell
Invoke-RestMethod "https://crates.io/api/v1/crates/bevy"
Invoke-RestMethod "https://crates.io/api/v1/crates/bevy_egui/0.43.1/dependencies"
```

### 否决一：`bevy-inspector-egui` 不能用

```text
bevy-inspector-egui 0.37.0 依赖：
  bevy_ecs      ^0.19.0
  bevy_reflect  ^0.19.0
  bevy_egui     ^0.40.0
  egui          ^0.34
```

当前 `bevy_egui 0.43.1` 要的是 Bevy 0.20 + egui 0.36。
**硬引入会让两个 Bevy 大版本共存 → 类型互不兼容 → 必然失败。**

**决定：自己实现 Inspector。**（这反而成了后面一个不错的设计。）

### 否决二：`egui` 不能升到最新的 0.37

```text
bevy_egui 0.43.1  →  egui ^0.36
egui_dock 0.21.1  →  egui ^0.36
而 crates.io 上 egui 最新是 0.37.0
```

若写 `egui = "0.37"`，会同时保留两个 `egui`，
于是 `egui_dock` 的 `TabViewer::ui(&mut Ui, ...)` 收到的 `Ui`
与它期望的 `Ui` 不是同一个类型。

**验证方式**（不是猜）：

```powershell
cargo tree -i egui --depth 1
```
```text
egui v0.36.2
├── bevy_egui v0.43.1
├── editor_app v0.1.0
├── editor_ui v0.1.0
└── egui_dock v0.21.1
```

三方收敛到同一个版本，无冲突。

### ⑦ 结论

```toml
bevy = "0.20.0"
bevy_egui = "0.43.1"
egui = "0.36"          # ← 不能写 0.37！
egui_dock = "0.21.1"
# bevy-inspector-egui：不引入，见 docs/技术选型.md
```

### ⑧ 经验

- **先跑 `cargo metadata` 再写代码**。依赖冲突早发现只要改一行 `Cargo.toml`；
  写完几千行再发现，排查成本高得多。
- 把"为什么钉在这个版本"写进 `Cargo.toml` 的注释里，
  后来者（包括三个月后的自己）不必重新调查。

## 第 2 步：分层——为什么要四层

### ② 原理：可测试性来自依赖方向

一个模块的可测试性，很大程度上取决于**它依赖了什么**。
如果"编辑器逻辑"依赖"窗口系统"，那么测试它就需要一个窗口。

**关键洞察**：编辑器里真正复杂的部分是**数据变换规则**
（层级怎么维护、撤销怎么回滚、保存怎么保证原子性），
而不是绘制。把数据变换抽到不依赖任何 GUI 的层里，
它们就能被毫秒级的单元测试覆盖。

### ③ 四层

```text
editor_app   ← 依赖 Bevy：窗口、渲染、插件装配
    ↓
editor_ui    ← 依赖 egui：面板绘制（只读数据、只产出意图）
    ↓
editor_core  ← 不依赖任何 GUI：命令、撤销、项目
    ↓
scene_doc    ← 不依赖任何 GUI：文档模型、序列化、存储
```

**依赖严格单向，下层完全不知道上层存在。**

### ④ 收益实测

```text
cargo test --workspace
  156 项通过，其中 152 项不需要窗口或 GPU
  最快的测试组（scene_doc / editor_ui）在 0.00s 完成
```

如果逻辑和 UI 混在一起，这 152 项里的绝大多数都无法自动化。

### ⑧ 经验

**分层不是为了好看，是为了可测。** 每当你发现"这段逻辑必须启动整个应用
才能验证"，就是一个把它抽出来的信号。

## 第 3 步：给资源路径套上类型

### ② 原理：在边界处校验，之后靠类型保证

这是类型驱动设计的核心技巧，也叫"parse, don't validate"。

**对比两种做法**：

```rust
// ❌ 校验散落各处：每个用到路径的地方都要重查一遍
fn 加载贴图(路径: &str) {
    if 路径.starts_with('/') { return; }
    if 路径.contains("..") { return; }
    // ... 而别的调用点可能忘了写这段
}

// ✅ 在边界处一次校验，之后靠类型保证
fn 加载贴图(路径: &项目相对路径) {
    // 不需要任何检查：能构造出这个类型就说明它合法
}
```

### ③ 要解决的三类真实故障

场景文件里的资源引用有三种典型故障，全部源于"路径就是一串自由文本"：

| 故障 | 例子 | 后果 |
| --- | --- | --- |
| 平台差异 | Windows 写 `textures\hero.png` | Linux 读不到 |
| 绝对路径污染 | 存了 `C:\Users\某人\...` | 换台机器立刻失效 |
| 目录穿越 | `../../etc/passwd` | 逃出项目根目录 |

### ⑤ 关键代码

```rust
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(transparent)]
pub struct 项目相对路径(String);      // ← 内部字段私有！
```

**字段私有是关键**：外部代码无法直接构造一个未经验证的路径，
必须走 `解析`。

```rust
pub fn 解析(输入: impl AsRef<str>) -> Result<Self, 路径错误> {
    let 原文 = 输入.as_ref();
    let 去空白 = 原文.trim();
    if 去空白.is_empty() {
        return Err(路径错误::空路径);
    }

    // 先把反斜杠统一成斜杠，再交给 Path 处理。
    let 统一 = 去空白.replace('\\', "/");

    // 显式拦截盘符与 UNC：`C:/x`、`//server/share`。
    if 统一.starts_with('/') {
        return Err(路径错误::绝对路径(原文.to_string()));
    }
    let bytes = 统一.as_bytes();
    if bytes.len() >= 2 && bytes[1] == b':' {
        return Err(路径错误::绝对路径(原文.to_string()));
    }

    let mut 段列表 = Vec::new();
    for 段 in 统一.split('/') {
        match 段 {
            "" => return Err(路径错误::空路径段(原文.to_string())),
            "." => continue,                                   // 忽略
            ".." => return Err(路径错误::目录穿越(原文.to_string())),
            _ => 段列表.push(段),
        }
    }
    // ... 还有一层 std::path 兜底（处理 `\\?\` 之类）
    Ok(Self(段列表.join("/")))
}
```

### ⑥ 测试

```rust
#[test]
fn 拒绝目录穿越() {
    assert!(matches!(
        项目相对路径::解析("../../secrets.txt"),
        Err(路径错误::目录穿越(_))
    ));
    assert!(matches!(
        项目相对路径::解析("assets/../../boom.png"),
        Err(路径错误::目录穿越(_))
    ));
}
```

### ⑦ 结果

```text
test path::测试::拒绝目录穿越 ... ok
test path::测试::拒绝绝对路径 ... ok
test path::测试::解析时统一分隔符 ... ok
（path.rs 共 7 项测试全部通过）
```

### ⑧ 经验

**校验逻辑只写一次，位置选在"数据进入系统"的边界处。**
之后在类型系统里携带这个保证，任何绕过它的代码都编译不过。

## 第 4 步：让"任意组件"都能被编辑

### ② 原理：把"能力"变成数据（表驱动）

Inspector 的朴素写法：

```rust
// ❌ 受支持组件清单硬编码在 UI 里
if 组件名 == "Sprite" {
    画颜色选择器(); 改 sprite.color;
} else if 组件名 == "Transform" {
    画三个拖动条(); 改 transform.translation;
}
// ... 每支持一个新组件都要改这里
```

问题：支持新组件 = 改 UI 代码；"哪些组件可编辑"散落在几十个分支里；
第三方无法扩展。

### ③ 反过来做：把描述变成数据

```rust
pub trait 组件类型: Send + Sync + 'static {
    fn 组件名(&self) -> &'static str;
    fn 默认实例(&self) -> Box<dyn Any>;
    fn 字段描述(&self) -> &[属性描述];
    fn 导出(&self, 实例: &dyn Any) -> Option<BTreeMap<String, 属性值>>;
    fn 实例化(&mut self, 实例: &mut dyn Any, 数据: &BTreeMap<String, 属性值>) -> bool;
}

pub struct 属性描述 {
    pub 字段名: String,
    pub 显示名: String,
    pub 种类: 属性种类,     // ← 决定画什么控件
    pub 默认值: 属性值,
    pub 提示: String,
    pub 只读: bool,
}

pub enum 属性种类 {
    布尔,
    整数 { 最小: Option<i64>, 最大: Option<i64> },
    浮点 { 最小: Option<f32>, 最大: Option<f32>, 步进: f32 },
    文本, 二维 { 步进: f32 }, 三维 { 步进: f32 }, 角度三维, 四维 { 步进: f32 },
    颜色,
    枚举 { 选项: Vec<(String, String, u32)> },
    资源 { 类别: 资源类别 },
    列表 { 元素: Box<属性种类> },
    结构 { 字段: Vec<属性描述> },
}
```

于是 Inspector 里**找不到任何具体组件的名字**：

```rust
fn 按描述编辑(ui: &mut Ui, 种类: &属性种类, 值: &mut 属性值, ...) -> bool {
    match 种类 {
        属性种类::布尔 => {
            let mut 开关 = 值.取布尔().unwrap_or(false);
            let 改变 = ui.checkbox(&mut 开关, "").changed();
            if 改变 { *值 = 属性值::布尔(开关); }
            改变
        }
        属性种类::浮点 { 最小, 最大, 步进 } => {
            let mut 数值 = 值.取浮点().unwrap_or(0.0);
            let mut 控件 = egui::DragValue::new(&mut 数值).speed(*步进);
            // 有范围限制才加 range
            let 改变 = ui.add(控件).changed();
            if 改变 { *值 = 属性值::浮点(数值); }
            改变
        }
        属性种类::颜色 => { /* 颜色选择器 */ }
        // ... 每种种类一个分支，但**没有任何组件名**
    }
}
```

### ⑤ 注册时校验：让配置错误在启动时暴露

```rust
pub fn 注册(&mut self, 类型: Box<dyn 组件类型>) -> Result<(), 注册表错误> {
    let 组件名 = 类型.组件名().to_string();
    for 描述 in 类型.字段描述() {
        if !描述.种类.接受(&描述.默认值) {
            return Err(注册表错误::默认值不匹配 {
                组件: 组件名.clone(),
                字段: 描述.字段名.clone(),
                种类: 描述.种类.类型名().to_string(),
                实际: 描述.默认值.种类名().to_string(),
            });
        }
    }
    // ...
}
```

有人把"布尔字段的默认值写成字符串"时，**程序启动就报错**，
而不是等用户点到那个字段才发现。

### ⑥ 测试

```rust
#[test]
fn 注册期校验默认值种类() {
    let mut 注册表 = 组件注册表::新建();
    let 结果 = 注册表.注册(Box::new(坏组件));
    match 结果 {
        Err(注册表错误::默认值不匹配 { 字段, .. }) => assert_eq!(字段, "开关"),
        其他 => panic!("期望默认值不匹配错误，实际：{其他:?}"),
    }
    // 校验失败不应污染注册表
    assert_eq!(注册表.数量(), 0);
}
```

### ⑦ 结果

支持一个新组件现在是：

1. 定义组件载体（若用引擎原生组件则跳过）；
2. 实现 `组件类型` 的五个方法；
3. 在插入逻辑里加一个 downcast 分支；
4. 注册。

**不改一行 UI 代码。**

### ⑧ 经验

当发现自己在写 `if 类型名 == "xxx"` 这样的分支时，
问一句：**这个分支能不能变成数据？**

## 第 5 步：场景文档的数据模型

### ② 原理：数据结构的选择决定算法复杂度

"场景是一棵树"这个直觉，会直接把数据结构写成嵌套的：

```rust
// ❌ 直觉写法
struct 场景实体 {
    名称: String,
    组件: Vec<组件数据>,
    子实体: Vec<场景实体>,      // ← 嵌套
}
```

在这种结构上，编辑器最常见的操作都是**最坏情况**：

| 操作 | 嵌套树 | 扁平表 + 父指针 |
| --- | --- | --- |
| 拖放改变层级 | 跨树搬移整个子树 + 重建两处容器 | 改一个字段 + 整理次序 |
| 按 ID 找实体 | O(n) | O(log n) |
| 删除子树 | 递归定位并搬移 | 收集后整体移除 |
| 撤销 | 深拷贝两棵树做 diff | 直接换引用 |

### ⑤ 实际结构

```rust
pub struct 场景文档 {
    pub 格式版本: u32,
    pub 元数据: 场景元数据,
    pub 实体表: BTreeMap<实体标识, 场景实体>,     // ← 扁平
    pub 顶层顺序: Vec<实体标识>,
    pub 资源表: BTreeMap<项目相对路径, 资源引用>,
}

pub struct 场景实体 {
    pub 标识: 实体标识,                    // ← 稳定身份
    pub 名称: String,
    pub 父实体: Option<实体标识>,          // ← 层级是隐式的
    pub 次序: u32,                        // ← 兄弟间唯一
    pub 变换: Option<变换数据>,
    pub 组件: Vec<组件数据>,               // Vec 保留用户添加顺序
    pub 编辑器隐藏: bool,                  // 编辑器专有元数据
    pub 编辑器锁定: bool,
    pub 编辑器展开: bool,
}
```

**为什么实体身份用 UUID 而不是序号**：序号在删除中间实体后会整体位移，
撤销栈、资源引用、外部工具里的引用**全部错位**。UUID 让身份与位置解耦。

**为什么用 `BTreeMap` 而不是 `HashMap`**：保存顺序必须稳定，
否则每次保存都产生无意义的文本 diff。

### ④ 代价：层级变成隐式的

必须靠校验保证一致性。这是**必须承认并处理的代价**，不能装作不存在：

```rust
pub fn 校验(&self) -> 文档校验报告 {
    let mut 报告 = 文档校验报告::default();

    // 1. 父实体存在性
    for (标识, 实体) in &self.实体表 {
        if let Some(父) = 实体.父实体 {
            if !self.实体表.contains_key(&父) {
                报告.悬空父实体.push(*标识);
            }
        }
    }

    // 2. 循环层级：向上走到超过实体总数，必然在环里
    let 上限 = self.实体表.len() + 1;
    for 标识 in self.实体表.keys() {
        let mut 当前 = *标识;
        let mut 步数 = 0;
        while let Some(父) = self.取(当前).and_then(|实体| 实体.父实体) {
            当前 = 父;
            步数 += 1;
            if 步数 > 上限 {
                报告.循环层级.push(*标识);
                break;
            }
        }
    }

    // 3. 次序冲突（按**实际父实体**分组）
    let mut 按父分组: HashMap<Option<实体标识>, HashMap<u32, Vec<实体标识>>> = HashMap::new();
    // ...

    // 4. 资源引用是否登记
    // ...
    报告
}
```

### ④ 校验的策略选择：报告而不是拒绝

一个层级轻微损坏的场景，**让用户能打开、看到问题、手工修好**，
比直接拒绝打开有用得多。唯一的例外是**格式版本过新** ——
那属于"语义未知"，强行解析会在保存时静默丢掉新版数据。

### ⑧ 踩到的坑（真实发生的）

**坑 1：分组键选错了**

最初用"是否出现在 `顶层顺序` 表里"作为分组键，
导致父实体为 `None` 但漏登记在 `顶层顺序` 里的实体被**错分成独立一组**，
既漏报它的次序冲突，也无法与兄弟比对次序。

**修复**：改为按**实际父实体**（`Option<实体标识>`）分组。

**坑 2：测试自己写错了**

测试 `悬空父实体与次序冲突会被校验发现` 失败：

```text
应当报告次序冲突，两者都要列出，
实际：文档校验报告 { 悬空父实体: [实体标识(9f70c135-...)], 次序冲突: [], ... }
```

根因：我把实体 A 的父实体改成不存在的幽灵，A 就不再是顶层实体；
同时又把实体 B 的次序改成 0。两者不在同一父分组下，**自然不构成次序冲突**。

**是测试写错了，不是校验器错了。**

**修复**：拆成两个独立测试，每个只验证一件事。

**经验**：测试失败时，**先判断是代码错了还是测试错了**。
两种都可能，而盲目改代码去迁就错误的测试会引入真正的 bug。

## 第 6 步：让保存变得安全

### ② 原理：原子性来自"重命名"

直接写目标文件是危险的：

```rust
// ❌ 写到一半断电 → 用户唯一的资产变成半截内容
let mut f = File::create(原文件)?;
f.write_all(内容)?;
```

**关键观察**：在同一个文件系统内，`rename` 是**原子**操作 ——
它要么指向旧内容，要么指向新内容，不存在中间态。

于是可以这样：

```text
1. 写 <场景>.tmp         内容不完整也只污染临时文件
2. 原文件改名 <场景>.bak   保留上一个完好版本
3. .tmp 改名到原文件       原子替换
成功后删 .bak；任一步失败则回滚
```

### ⑤ 关键代码

```rust
fn 写入(&self, 路径: &Path, 文档: &场景文档) -> 场景结果<保存结果> {
    let 已存在 = 路径.is_file();
    let 文本 = 编码场景(文档)?;
    let 临时 = Self::临时路径(路径);
    let 备份 = Self::备份路径(路径);

    // 第 1 步：完整写入临时文件并落盘。
    {
        use std::io::Write;
        let mut 句柄 = std::fs::File::create(&临时)?;
        句柄.write_all(文本.as_bytes())?;
        句柄.flush()?;
        // ↓ 关键：不 sync_all 的话，数据可能只在内核页缓存里，
        //   断电后重命名成功但内容是空的。
        句柄.sync_all()?;
    }

    // 第 2 步：把现有文件挪到备份。
    if 已存在 {
        let _ = std::fs::remove_file(&备份);
        if let Err(错误) = std::fs::rename(路径, &备份) {
            let _ = std::fs::remove_file(&临时);       // 清理，不留垃圾
            return Err(场景错误::保存失败 { ... });
        }
    }

    // 第 3 步：临时文件就位。
    if let Err(错误) = std::fs::rename(&临时, 路径) {
        // 回滚：把备份搬回原位，保证用户的原文件不丢
        if 已存在 {
            let _ = std::fs::rename(&备份, 路径);
        }
        let _ = std::fs::remove_file(&临时);
        return Err(场景错误::保存失败 { ... });
    }
    // ...
}
```

### ④ 读取端也必须配合

写端保证"最坏情况下总有一个完好的文件"，读端必须去找它：

```rust
fn 读取(&self, 路径: &Path) -> 场景结果<读取结果> {
    let 候选 = [
        (路径.to_path_buf(), false),
        (Self::备份路径(路径), true),
        (Self::临时路径(路径), true),
    ];
    let 存在列表: Vec<_> = 候选.into_iter()
        .filter(|(候选路径, _)| 候选路径.is_file())
        .collect();

    for (候选路径, 从备份) in 存在列表 {
        let 文本 = match std::fs::read_to_string(&候选路径) { Ok(t) => t, Err(e) => { ...继续 } };
        // ↓ 关键：**完整解析成功**才算这个候选可用
        match 解码场景(&文本, &候选路径) {
            Ok(文档) => return Ok(读取结果 { 文档, 来源路径: 候选路径, 从备份恢复: 从备份 }),
            Err(错误) => { 最后错误 = Some(错误); }     // 继续试下一个候选
        }
    }
    Err(最后错误.unwrap_or_else(...))
}
```

**"每个候选都必须完整解析成功"这一点极其重要。**
只检查"文件是否存在"是不够的：一个存在但内容损坏的原文件
会让读取提前失败，从而**永远用不上完好的备份**。

### ⑥ 测试

```rust
#[test]
fn 保存失败时原文件不被破坏() {
    let 存储 = 临时存储::新建();
    存储.写入(&路径, &第一版).unwrap();
    let 写入前内容 = 存储.取出(&路径).unwrap();

    存储.设置写入失败("磁盘已满");
    let 结果 = 存储.写入(&路径, &第二版);
    assert!(结果.is_err());

    assert_eq!(存储.取出(&路径).as_deref(), Some(写入前内容.as_str()),
               "保存失败后原文件内容被改动了");
}
```

### ⑧ 踩到的坑：测试替身与生产实现语义不一致

`临时存储`（测试用）最初只检查"原文件键是否存在"，
一旦存在就直接解析，**解析失败就抛错**，走不到备份。
而 `文件系统场景存储`（生产用）是正确的。

后果：**测试通过也不能证明生产代码正确** —— 两者语义不同。

**修复**：把 `临时存储::读取` 改成与生产实现同样的语义。

**这是本教程里最值得记住的教训之一**：
测试替身必须与真实实现保持**语义一致**，否则测试是自我安慰。

## 第 7 步：把修改表达成数据

### ② 原理：单一实现 vs 多处实现

需求里有一条硬约束：

> 保存、撤销、重做、复制、粘贴等操作必须共享一致的数据修改规则。

**朴素做法的问题**：

```rust
// 右键菜单
fn 删除实体_右键(状态: &mut 状态, 标识: 标识) {
    状态.文档.删除(标识);
    状态.撤销栈.记录(...);        // ← 容易忘
    状态.选择.清理(标识);         // ← 容易忘
}

// 工具栏
fn 删除实体_工具栏(状态: &mut 状态, 标识: 标识) {
    状态.文档.删除(标识);
    // ← 忘了记录撤销，用户按 Ctrl+Z 撤销不了
}
```

规模一大，某条路径漏了撤销记录或漏清理选择集，
就会出现"撤销后场景错乱"。

### ⑤ 改成数据

```rust
#[derive(Debug, Clone, PartialEq)]
pub enum 编辑器命令 {
    新建实体 { 名称: String, 父实体: Option<实体标识>, 指定标识: Option<实体标识> },
    删除实体 { 标识: 实体标识 },
    重命名实体 { 标识: 实体标识, 新名称: String },
    重设父子 { 标识: 实体标识, 新父实体: Option<实体标识>, 新次序: u32 },
    上移实体 { 标识: 实体标识 },
    下移实体 { 标识: 实体标识 },
    设变换 { 标识: 实体标识, 变换: Option<变换数据> },
    批量设变换 { 项: Vec<(实体标识, Option<变换数据>)> },
    添加组件 { 标识: 实体标识, 组件: 组件数据 },
    删除组件 { 标识: 实体标识, 类型名: String },
    设组件属性 { 标识: 实体标识, 类型名: String, 属性名: String, 新值: 属性值 },
    批量设属性 { 项: Vec<(实体标识, String, String, 属性值)> },
    替换实体 { 实体: Box<场景实体> },
    设为快照 { 文档: Box<场景文档> },
}
```

所有入口都只做一件事：

```rust
编辑器状态::执行(命令)
```

### ④ 事务边界

```rust
pub fn 执行(&mut self, 命令: 编辑器命令) -> 场景结果<命令结果> {
    let 执行前 = Arc::new(self.会话.文档.clone());

    // 在**克隆**上执行 —— 失败时正本未被触碰。
    let mut 工作副本 = self.会话.文档.clone();
    let 结果 = 命令.应用(&mut 工作副本)?;      // ← 失败直接返回，正本没动过

    // 成功：提交回正本并记录撤销条目。
    self.会话.文档 = 工作副本;
    self.撤销.提交(命令, 执行前, 结果.新实体);

    // 选择集必须跟着文档走，否则删除后会出现"幽灵选中"。
    self.选择.清理失效项(&self.会话.文档);

    Ok(结果)
}
```

**"在克隆上执行"是同时满足这两个要求的关键**：

- 命令**可以**部分执行后失败（批量操作中途某项非法）；
- 失败**必须**不留痕迹。

否则就要为每条命令写反向操作 —— 而这正是下一步要避开的。

### ⑧ 经验

**当发现"同一个逻辑要在多处保持同步"时，就把它变成数据。**

## 第 8 步：撤销栈——一个反直觉的选择

### ② 原理：正确性的来源越少越好

主流做法是给每个操作写 `undo()`。它省内存，但代价是
**每条命令都必须有人正确写出反向语义**。而这些反向语义都不显然：

| 操作 | 反向要做的事 |
| --- | --- |
| 删除实体连同整棵子树 | 按原次序、原父实体精确复原 |
| 调整层级 | 复原新旧**两侧**的次序编号 |
| 拆除组件 | 复原组件的完整属性表 |

任何一处写错，表现就是"撤销之后场景悄悄坏掉"，**很难定位**。

### ④ 反直觉的选择：全量快照 + 命令重放

```text
撤销条目 {
    标记: u64,
    显示名: String,
    执行前: Arc<场景文档>,     // ← 变更前的整份文档
    命令: 编辑器命令,
    新实体: Option<实体标识>,
}

撤销 = 把当前文档覆盖为「执行前」快照
重做 = 重新应用命令
```

**正确性只依赖两件已经有测试覆盖的事**：

1. 文档能 `Clone`；
2. 命令能 `apply`。

这比"每条命令都写对反向操作"要容易验证得多。

### ④ 代价与处理

代价是内存。用**字节预算**约束：

```rust
pub const 默认内存预算字节: usize = 64 * 1024 * 1024;
pub const 默认最大步数: usize = 256;

fn 收缩到预算内(&mut self) {
    while self.已应用.len() > self.最大步数 && self.已应用.len() > 1 {
        self.已应用.remove(0);
    }
    while self.估算字节() > self.内存预算 && self.已应用.len() > 1 {
        self.已应用.remove(0);
    }
}
```

超预算从最旧一端丢弃条目 —— **只影响"能撤销多少步"，
不影响撤销是否正确**。

**刻意不调用序列化来精确测量内存**：那会让每次提交都付出一次
全量序列化的代价，正是需求里禁止的"每次修改都重新序列化整个项目"。

### ④ 保存点为什么用标记而不是下标

"文档是否已保存"需要记录保存时的栈位置。用下标的话：

```text
栈: [A, B, C, D]   保存点在 C（下标 2）
丢弃最旧 → [C, D]   下标全部位移，保存点变成 0 → 指向 C？不对，是 C 没错
再丢弃  → [D]       保存点 0 → 指向 D ← 错了！
```

**症状**：表现为"存过盘的文件仍显示未保存"，
或更糟的"没存盘却显示已保存"（用户以为存好了，关掉编辑器丢数据）。

**解法**：每个条目带一个**只增不减**的标记，比较标记即可：

```rust
pub fn 标记已保存(&mut self) {
    self.保存点 = self.当前位置标记();
}

pub fn 有未保存修改(&self) -> bool {
    self.保存点 != self.当前位置标记()
}
```

### ⑥ 测试

```rust
#[test]
fn 丢弃最旧条目不会破坏保存点的正确性() {
    // 这是"用标记而不是下标"的直接验证：
    // 先在栈空时标记保存，再压入超过上限的条目把最旧的冲掉，
    // 此时应当仍然报告"已修改"。
    let mut 栈 = 撤销栈::带预算(usize::MAX, 2);
    栈.标记已保存();
    for 序号 in 0..5 {
        栈.提交(命令(&format!("第{序号}次")), 快照("基线"), None);
    }
    assert!(栈.有未保存修改(), "内容与保存点不同时必须报告已修改");
    assert_eq!(栈.保存点, None);
}
```

### ⑧ 经验

**选择"正确性更容易证明"的方案，而不是"更省资源"的方案。**
省下的资源可以后续优化；而难以证明的正确性会持续产生 bug。

## 第 9 步：重做幂等——一个差点漏掉的深坑

这一节单独成节，因为它是整个项目里**最有价值的教训**。

### ① 问题是怎么发现的

测试 `里程碑B_撤销重做能精确还原属性修改` 失败：

```text
DEBUG 重做=true
      实体=实体标识(fc978bd3-4eac-41c8-a984-94e9a5ae2b5d)
      存在=false
      文档实体=[实体标识(314ef5bb-d4b4-434b-91a9-9665aaf4b927)]   ← 标识变了！
```

**现象**：重做之后"新建实体"这一步，实体**确实被创建了**，
但**标识和原来不一样**。

### ② 根因

```rust
编辑器命令::新建实体 {
    名称: String,
    父实体: Option<实体标识>,
    指定标识: Option<实体标识>,      // ← 首次执行时是 None
}
```

首次执行时 `指定标识 = None`，**UUID 由执行过程生成**。
重做时重新执行**原始命令**，于是**又生成了一个不同的 UUID**。

### ② 为什么这个 bug 极其危险

后果是所有记录了标识的外部状态**全部静默失效**：

- 选择集（撤销再重做后，选中的实体"不存在了"）
- 剪贴板
- 资源引用
- 用户脚本里按标识查找实体的代码

而且**极难被发现**：因为文档看起来"有那个实体"，
只是它的标识变了。用户只会说"撤销重做之后有点怪"，说不清哪里怪。

### ⑤ 修复：让重做幂等

**三步**：

1. 撤销条目新增字段记录首次生成的标识：

```rust
pub struct 撤销条目 {
    pub 标记: u64,
    pub 显示名: String,
    pub 执行前: Arc<场景文档>,
    pub 命令: 编辑器命令,
    /// 首次执行该命令时新生成的实体标识（若有）。
    pub 新实体: Option<实体标识>,      // ← 新增
}
```

2. 提交时记录它：

```rust
self.撤销.提交(命令, 执行前, 结果.新实体);
```

3. 重做时把它填回命令：

```rust
impl 撤销条目 {
    /// 返回一条用于**重做**的命令。
    ///
    /// 与原始命令的唯一区别是把首次生成的实体标识填回去，
    /// 保证重做产生与首次执行完全相同的文档。
    pub fn 重做用命令(&self) -> 编辑器命令 {
        match (&self.命令, self.新实体) {
            (
                编辑器命令::新建实体 { 名称, 父实体, 指定标识: None },
                Some(标识),
            ) => 编辑器命令::新建实体 {
                名称: 名称.clone(),
                父实体: *父实体,
                指定标识: Some(标识),        // ← 填回去
            },
            _ => self.命令.clone(),
        }
    }
}
```

### ⑥ 补测试守住它

**修复 bug 之后最重要的一步不是改代码，而是加测试。**

```rust
#[test]
fn 重做命令会把首次生成的实体标识填回去() {
    // 这是"重做必须幂等"的单元级验证。
    // 若不填回标识，重做会生成新 UUID，外部记录的标识全部失效。
    let 指定 = 实体标识::新建();
    let 条目 = 撤销条目 {
        标记: 1,
        显示名: "新建实体".to_string(),
        执行前: 快照("基线"),
        命令: 编辑器命令::新建实体 {
            名称: "甲".to_string(),
            父实体: None,
            指定标识: None,               // ← 首次执行时是 None
        },
        新实体: Some(指定),
    };

    match 条目.重做用命令() {
        编辑器命令::新建实体 { 指定标识, .. } => {
            assert_eq!(指定标识, Some(指定),
                "重做时必须复用首次生成的实体标识，否则重做后标识会漂移");
        }
        其他 => panic!("重做命令的类型不应改变，实际：{其他:?}"),
    }
}
```

以及集成层的：

```rust
// 一路撤销到底：实体应当消失
推动作(&mut 世界, vec![UiAction::撤销, UiAction::撤销, UiAction::撤销]);
执行动作(&mut 世界);
assert!(!取编辑器(&世界).状态.会话.文档.存在(实体));

// 重做必须把**同一个**标识找回来
推动作(&mut 世界, vec![UiAction::重做]);
执行动作(&mut 世界);
assert!(取编辑器(&世界).状态.会话.文档.存在(实体),
    "重做之后实体标识必须与原来完全相同，否则选择集与引用会全部失效");
```

### ⑦ 结果

```text
test undo::测试::重做命令会把首次生成的实体标识填回去 ... ok
test 通过动作队列可以撤销重做且标识保持不变 ... ok
```

### ⑧ 经验（这一节的核心）

1. **任何"让系统回到之前状态"的操作，都要问一句：它真的回到了那个状态吗？**
   不只是"看起来一样"，而是**所有标识与引用都一样**。
2. **重新执行一条命令 ≠ 重放它造成的效果。** 若命令里有任何
   "由执行过程生成"的值（UUID、时间戳、随机数），
   重新执行就会产生不同的结果。这些值必须被记录下来。
3. **修复 bug 之后立刻补测试。** 这个坑很隐蔽，
   没有测试守着，将来重构时很容易再犯。

## 第 10 步：界面不直接改数据

### ② 原理：单向数据流

```text
用户操作
  → 面板把操作翻译成 UiAction 排进队列
  → editor_app 在下一帧统一执行
  → 编辑器状态::执行(命令)
```

### ④ 为什么不是"面板里直接改"

**三个真实的原因**（不是理论洁癖）：

**原因 1：借用检查器不允许**

egui 的闭包里拿着文档的不可变借用：

```rust
egui::ScrollArea::show(ui, |ui| {
    for 行 in &全部行 {              // ← 借用 上下文.编辑器.会话.文档
        if 按钮.clicked() {
            上下文.编辑器.删除实体(...);   // ❌ 同时可变借用 → 编译不过
        }
    }
});
```

**原因 2：可测试性**

面板绘制函数可以只检查"点了按钮是否产生了正确的意图"，
不需要跑起整个 Bevy 应用。

**原因 3：横切规则只需要写一次**

"保存前先同步资源表"、"删除资源前先检查引用"这类规则
如果散在每个面板里，迟早会漏。

### ⑤ 关键代码

```rust
/// 界面向编辑器发出的意图。
pub enum UiAction {

```

执行器是**唯一**修改编辑器状态的地方：

```rust
pub fn 执行动作队列(
    mut 界面: ResMut<UiStateHolder>,
    mut 编辑器: ResMut<EditorStateHolder>,
    mut 运行时: ResMut<运行时宿主>,
    mut 对话框: ResMut<文件对话框通道>,
    mut 拖动: Local<拖动快照>,
) {
    let 动作列表 = 界面.动作.取出();
    if 动作列表.is_empty() { return; }

    // 拖动中的高频动作合并成一条
    let 动作列表 = 合并拖动动作(动作列表);

    for 动作 in 动作列表 {
        if let UiAction::聚焦面板(面板) = &动作 {
            界面.状态.聚焦面板(*面板);
            continue;
        }
        执行单个动作(&mut 编辑器.状态, &mut 运行时, &mut 对话框, &mut 拖动, 动作);
    }
    // ... 清理失效选择
}
```

### ④ 一个真实的细节：同帧动作合并

一次拖动会产生几十条 `拖动实体到`。如果每条都执行，
撤销栈会被瞬间填满，用户按一次 Ctrl+Z 只能退回**一个鼠标像素**。

```rust
fn 合并拖动动作(动作列表: Vec<UiAction>) -> Vec<UiAction> {
    let mut 结果: Vec<UiAction> = Vec::with_capacity(动作列表.len());
    for 动作 in 动作列表 {
        if matches!(动作, UiAction::拖动实体到 { .. }) {
            // 丢掉之前累积的同类动作，只保留最新位置
            if let Some(位置) = 结果.iter()
                .rposition(|已有| matches!(已有, UiAction::拖动实体到 { .. }))
            {
                结果.remove(位置);
            }
        }
        结果.push(动作);
    }
    结果
}
```

而且拖动位置的计算**以按下位置为基准**，不是逐帧累加：

```rust
UiAction::拖动实体到 { 世界偏移 } => {
    // 以拖动开始时的位置为基准加上偏移
    let 项: Vec<_> = 拖动.项.iter().map(|(标识, 起始)| {
        let mut 新变换 = *起始;
        新变换.平移.0 = 起始.平移.0 + 世界偏移.0;
        新变换.平移.1 = 起始.平移.1 + 世界偏移.1;
        (*标识, Some(新变换))
    }).collect();
    编辑器.执行并记录(编辑器命令::批量设变换 { 项 });
}
```

逐帧累加会因浮点误差与丢帧而漂移，快速拖动时表现为
**对象慢慢偏离鼠标**。基于起始值计算是幂等的，反复执行不累积误差。

### ⑧ 踩到的坑

集成测试 `通过动作队列可以新建实体并被自动选中` 失败：

```text
left: None   right: Some(实体标识(902bff1c-...))
```

根因：执行器的 `UiAction::执行命令` 分支用的是 `执行并记录`，
**不是** `执行并选中`。效果是菜单里点"新建实体"，
场景树多了一项，但检查器仍显示"未选中任何实体"。

**这个缺陷在 core 层也出现过一次**（第 7 步提到的 `新建实体` 用错了方法），
只是路径不同。**只测其中一条会漏掉另一条** —— 这是集成测试的价值所在。

**修复**：只对 `新建实体` 这一类命令走 `执行并选中`：

```rust
if matches!(命令, 编辑器命令::新建实体 { .. }) {
    if let Err(错误) = 编辑器.执行并选中(命令) {
        编辑器.错误(format!("操作失败：{错误}"));
    }
} else {
    编辑器.执行并记录(命令);
}
```

**为什么不给所有命令都做选中**：删除一个东西之后自动选中别的东西
会让用户困惑。

## 第 11 步：把逻辑从绘制里挤出来

### ② 原理：纯函数最好测

界面代码难测，是因为它通常混合了两件事：

1. **逻辑**：算出要显示什么（哪些行、什么顺序、什么颜色、能不能点）
2. **绘制**：把这些东西画到屏幕上

**把第 1 件事抽成纯函数**，它就能被毫秒级测试覆盖。

### ⑤ 例子 1：场景树的摊平与过滤

```rust
/// 把场景文档摊平成场景树显示行。
pub fn 构建显示行(文档: &场景文档) -> Vec<显示行> {
    let mut 结果 = Vec::new();
    for (标识, 深度) in 文档.深度优先遍历() {
        let Some(实体) = 文档.取(标识) else { continue };
        结果.push(显示行 {
            标识,
            名称: 实体.名称.clone(),
            深度,
            有子实体: !文档.子实体列表(Some(标识)).is_empty(),
            隐藏: 实体.编辑器隐藏,
            锁定: 实体.编辑器锁定,
            展开: 实体.编辑器展开,
        });
    }
    结果
}
```

**过滤时保留祖先**（这是一个容易做错的细节）：

```rust
pub fn 按名称过滤(行列表: &[显示行], 关键字: &str) -> Vec<显示行> {
    let 关键字 = 关键字.trim();
    if 关键字.is_empty() { return 行列表.to_vec(); }

    // 先按深度栈求出每一行的祖先链。
    let mut 保留 = vec![false; 行列表.len()];
    let mut 栈: Vec<usize> = Vec::new();
    for (下标, 行) in 行列表.iter().enumerate() {
        while 栈.len() > 行.深度 { 栈.pop(); }
        let 命中 = 行.名称.contains(关键字);
        if 命中 {
            保留[下标] = true;
            for 祖先 in &栈 { 保留[*祖先] = true; }    // ← 祖先一起保留
        }
        栈.push(下标);
    }
    // ...
}
```

**为什么**：只保留匹配项本身，结果看起来"孤零零挂在根上"，
用户无法判断它在层级里的位置。

### ⑤ 例子 2：菜单可用性变成数据

```rust

            可用性::需要可撤销 => 编辑器.撤销.可撤销步数() > 0,

```

于是菜单项定义就是数据：

```rust

菜单项::常可用("删除实体", Some("Delete")).需要(可用性::需要选中),
菜单项::常可用("撤销", Some("Ctrl+Z")).需要(可用性::需要可撤销),
```

数据化之后可以写测试断言这条：

### ⑤ 例子 3：视口命中测试

```rust
/// 命中测试：返回世界坐标点下最靠上的实体。
pub fn 命中测试(文档: &场景文档, 世界点: (f32, f32)) -> Option<实体标识> {
    let 顺序 = 文档.深度优先遍历();
    // 倒序查找：后画的（在场景树里靠后的）优先命中，与视觉直觉一致

        let Some(实体) = 文档.取(*标识) else { continue };
        // 锁定与隐藏的实体不可被选中
        if 实体.编辑器锁定 || 实体.编辑器隐藏 { continue; }
        if let Some(框) = 计算实体框(文档, *标识) {
            if 框.包含(世界点) { return Some(*标识); }
        }
    }
    None
}
```

## 第 12 步：单向桥接与物理隔离

### ② 原理：隔离靠数据分离，不靠约定

需求明确要求：

> 运行时对实体、组件和资源的临时修改，不应自动写回编辑器文档。

**弱做法**：约定"运行时不要改编辑器数据" —— 迟早有人违反。

**强做法**：让运行时数据**根本不在同一个地方**。

### ⑤ 结构

```text
场景文档  ──[构建世界]──►  独立的 Bevy World（运行时宿主持有）
    ▲                            │
    │                            │  只读地取统计数据
    └────── 绝不自动回写 ─────────┘
```

```rust
#[derive(Resource)]
pub struct 运行时宿主 {
    pub 状态: 运行状态,
    /// 运行时世界。停止时为 `None`。
    pub 世界: Option<World>,              // ← 独立的 World
    pub 映射: 实体映射表,
    pub 启动快照: Option<场景文档>,
    pub 上次统计: 构建统计,
    // ...
}

impl 运行时宿主 {
    pub fn 启动(&mut self, 文档: &场景文档, 注册表: &组件注册表) {
        let mut 世界 = World::new();
        世界.insert_resource(Time::<()>::default());
        let (统计, 映射) = 构建世界(&mut 世界, 文档, 注册表);
        self.世界 = Some(世界);
        // ...
    }

    /// 停止并丢弃运行时世界。
    ///
    /// 丢弃是整个隔离方案的最后一步：运行时的所有修改随 `World` 一起消失，
    /// 不可能有机会回写编辑器文档。
    pub fn 停止(&mut self) {
        self.世界 = None;
        self.映射.清空();
        self.状态 = 运行状态::已停止;
    }
}
```

### ④ 为什么必须独立 `World`

如果把运行时实体直接生成在**编辑器主世界**里：

1. "停止运行"必须**逐个清理**，一旦漏掉就留下幽灵实体；
2. 游戏逻辑会直接改到编辑器正在显示的数据。

放在独立的 `World` 里，停止时把它置空，运行时数据**整体消失** ——
不存在"清理漏了哪个"的问题。

### ⑤ 构建世界分两趟

```rust
pub fn 构建世界(世界: &mut World, 文档: &场景文档, 注册表: &组件注册表)
    -> (构建统计, 实体映射表)
{
    let mut 待建父子: Vec<(实体标识, 实体标识)> = Vec::new();

    // ---- 第一趟：实体与组件 ----
    for 标识 in &全部标识 {
        let 运行时实体 = 世界.spawn_empty().id();
        映射.插入(*标识, 运行时实体);
        世界.entity_mut(运行时实体).insert(Name::new(实体数据.名称.clone()));
        if let Some(变换) = 实体数据.变换 {
            世界.entity_mut(运行时实体).insert(变换数据转_bevy(变换));
        }
        // 其余组件按注册表逐个应用
        for 组件 in &实体数据.组件 { /* ... */ }

        if let Some(父) = 实体数据.父实体 {
            待建父子.push((*标识, 父));      // ← 记下来，第二趟再建
        }
    }

    // ---- 第二趟：父子关系 ----
    for (子, 父) in 待建父子 {
        let (Some(父实体), Some(子实体)) = (映射.取运行时(父), 映射.取运行时(子)) else {
            continue;      // 悬空父实体：保持子实体为顶层，而不是丢弃它
        };
        世界.entity_mut(子实体).insert(ChildOf(父实体));
    }
    // ...
}
```

**为什么必须两趟**：建立父子关系时父实体必须已存在，
而文档里的实体顺序不保证父在子之前（`BTreeMap` 按 UUID 排序）。

### ⑥ 测试

```rust
#[test]
fn 运行时的修改不会影响文档快照() {
    let mut 文档 = 场景文档::新建("隔离测试");
    let 标识 = 文档.生成实体("玩家", None);
    let 文档备份 = 文档.clone();

    let mut 宿主 = 运行时宿主::default();
    宿主.启动(&文档, &注册表);

    // 在运行时世界里修改实体
    let 运行时实体 = 宿主.映射.取运行时(标识).unwrap();
    let 世界 = 宿主.世界.as_mut().unwrap();
    世界.entity_mut(运行时实体).insert(Transform {
        translation: Vec3::new(999.0, 999.0, 999.0), ..default()
    });
    世界.despawn(运行时实体);

    // 运行时世界里确实少了这个实体
    // （否则下面的隔离断言就没有说服力：
    //   如果运行时根本没被改动，"文档没变"是理所当然的）
    assert_eq!(宿主.运行时实体数(), 0,
        "运行时实体已被销毁，运行时实体数应当变为 0");

    // 文档必须一字未改
    assert_eq!(文档, 文档备份, "运行时修改绝不能写回场景文档");
    assert!(文档.存在(标识));
}
```

**注意那个注释**：先证明"被隔离的那一侧真的变了"，
隔离断言才有说服力。这是一个容易忽略的测试设计要点。

### ⑧ 踩到的坑 1：统计口径错误

测试 `运行时宿主启动停止后世界被彻底丢弃` 失败：

```text
left: 4   right: 2      （文档里只有 2 个实体）
```

打印世界里所有实体：

```text
DEBUG count_spawned=4 len=4
      实体列表=[(0v0, None), (1v0, None), (2v0, Some("甲")), (3v0, Some("乙"))]
```

**根因**：实体索引 0 与 1 **没有名字** —— 它们是 `World::new()`
本身创建的 **2 个内部基础设施实体**。

而且原来的实现用 `entities().len()`，它返回**曾经分配过**的索引数量，
实体 `despawn` 后索引不回收，因此只增不减。

**修复**：改为统计"带 `Name` 组件"的实体。
`构建世界` 会给每一个由场景文档创建出来的实体都插入 `Name`，
所以这个判据与"场景实体"的定义严格一致。

### ⑧ 踩到的坑 2：类型擦除隐藏的不变量

测试 `未注册组件被跳过但不影响其他组件` 失败：

```text
left: 2   right: 1      （期望只跳过 1 个未知组件）
```

**根因**：`可见性属性` 的 `实例化` 能成功，
但 `插入已知组件` 里**没有它的 downcast 分支** ——
我只写了 `downcast_ref::<Visibility>()`，而实际实例是编辑器自己的
包装类型。于是插入返回 `false`，被计入"跳过"。

**这类缺陷编译器抓不到**，因为 `组件类型` 是**类型擦除**的：
注册表里加了类型、插入逻辑漏了分支，编译器不会有任何意见。

**后果很隐蔽**：注册表里有、属性也写进去了、运行时统计却把它算成
"跳过"，组件静默失效。

**修复分两步**：

1. 补上分支；
2. **新增测试守住这条不变量**：

```rust
/// 守住"注册表里的每个类型都必须有插入分支"这条不变量。
///
/// 这条不变量无法用类型系统表达（`组件类型` 是类型擦除的），
/// 而漏掉一个分支的后果很隐蔽。因此用测试把每个已注册类型
/// 都实际走一遍插入路径。
#[test]
fn 注册表与插入分支一一对应() {
    let 注册表 = 默认组件注册表();

    for 类型名 in 注册表.组件名列表() {
        let 类型 = 注册表.要求(&类型名).unwrap();
        let mut 实例 = 类型.默认实例();

        // 用声明出的默认值构造一份合法属性表
        let mut 属性 = std::collections::BTreeMap::new();
        for 描述 in 类型.字段描述() {
            属性.insert(描述.字段名.clone(), 描述.默认值.clone());
        }
        assert!(类型.实例化(实例.as_mut(), &属性),
            "组件 `{类型名}` 的实例化失败了");

        // 关键断言：必须能被插入世界
        let mut 世界 = World::new();
        let 实体 = 世界.spawn_empty().id();
        assert!(插入已知组件(&mut 世界, 实体, 实例.as_ref()),
            "组件 `{类型名}` 在 `插入已知组件` 里没有对应的分支；\
             注册表与插入逻辑必须保持一一对应");
    }
}
```

### ⑧ 经验

**当类型系统无法表达某个不变量时，用测试把它固定下来。**
上面这个测试比修复本身更有价值：它把"只能靠人记得"的约束
变成了自动化检查。

## 第 13 步：测试没覆盖到的那一层

### ① 为什么还要再写一层测试

到第 12 步为止，每一层都有自己的测试。但它们验证的是
**"API 能工作"**，而不是**"用户动作真的能走通整条链路"**。

从"用户点击"到"文档变化"之间还有三个环节：

1. **动作分派**：`执行动作队列` 的 match 分支是否接对了？
2. **上下文参数**：`Local<拖动快照>`、`ResMut` 是否正确传递？
3. **资源变更可见性**：系统改完后，从外部读到的资源是否是新值？

## 结语：这套方法可以迁移到哪里

回顾整个开发过程，反复出现的模式其实只有几条：

### 1. 先核实，再设计

- 用 crates.io API 查真实版本，而不是凭记忆
- 用最小复现实验证明环境可用，而不是读环境变量猜
- 先跑 `cargo metadata` 验证依赖树，再写代码

**收益**：两次关键否决（`bevy-inspector-egui`、`egui 0.37`）
如果留到写代码之后才发现，代价会大得多。

### 2. 在边界处校验，之后靠类型保证

- `项目相对路径` 内部字段私有，构造即校验
- 组件注册表在**注册时**校验默认值

**收益**：校验逻辑只写一次，不会因为新增调用点而漏掉。

### 3. 把逻辑变成数据

- 修改 → `编辑器命令` 枚举
- 组件字段 → `属性描述` 数据
- 菜单可用性 → `可用性` 枚举

**收益**：单一实现、可序列化、可测试、第三方可扩展。

### 4. 选择"正确性更容易证明"的方案

- 撤销用快照 + 重放，而不是反向操作
- 隔离靠两份数据，而不是靠清理逻辑写对

**收益**：正确性依赖的前提更少，出 bug 的面更小。

### 5. 把逻辑从绘制里挤出来

- 场景树摊平、资源树构建、命中测试、菜单可用性全是纯函数

**收益**：156 项测试里 152 项不需要窗口或 GPU。

### 6. 修 bug 之后立刻补测试

- 重做幂等性
- 注册表与插入分支一一对应
- 保存点用标记而非下标

**收益**：把一个"很难再发现"的问题变成永久性的自动检查。

### 7. 诚实记录未验证与未实现的部分

- README 用一整节列出"不能做什么"
- 未实现的菜单项显示为禁用，不假装可用
- 工作日志记录"界面渲染没有像素级验证"这样的缺口

**收益**：使用者不会被误导；后来者知道从哪里接手。
