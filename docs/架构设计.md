# 架构设计

本文说明 Bevy Studio 的整体架构、模块边界与数据流，
并在每个关键决策处解释**为什么这样设计**以及**代价是什么**。

---

## 一、设计约束

架构不是凭空设计的，它由下面这些硬约束推导出来：

| 约束 | 来源 | 对架构的影响 |
| --- | --- | --- |
| 编辑器文档与运行时 ECS 世界不能混为一体 | 需求 | 运行时必须住在独立的 `World` 里 |
| 场景数据必须有明确、稳定的序列化格式 | 需求 | 文档层不依赖 Bevy，格式与引擎类型解耦 |
| 所有修改必须通过统一的命令/事务机制 | 需求 | 单一 `执行(命令)` 入口，界面不直接改数据 |
| 保存、撤销、重做、复制、粘贴共享一致的修改规则 | 需求 | 修改表达为**数据**（命令枚举），撤销只有一份实现 |
| 资源路径与 UUID 必须能稳定引用资源 | 需求 | `项目相对路径` + `资源唯一标识` 双层引用 |
| 运行时临时状态不能覆盖编辑器已保存状态 | 需求 | 单向桥接 + 停止时整体丢弃 `World` |
| 避免循环依赖与无法测试的巨型系统 | 需求 | 四层单向依赖；逻辑层不依赖 Bevy，可在 CI 完整测试 |
| 引擎会升级 | 工程现实 | 场景格式独立于引擎版本 |

---

## 二、分层

```text
┌──────────────────────────────────────────────────────────────────┐
│  editor_app        随进程     依赖 Bevy                          │
│  ── Bevy 插件装配、组件注册表、场景 ⇄ ECS 桥接、文件对话框线程    │
└───────────────────────────┬──────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────┐
│  editor_ui         随帧       只依赖 egui / egui_dock             │
│  ── 面板绘制、布局、主题；只读编辑器状态，只产出 UiAction          │
└───────────────────────────┬──────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────┐
│  editor_core       随会话     不依赖 Bevy                          │
│  ── 编辑器状态、命令、撤销栈、项目模型、选择集                     │
└───────────────────────────┬──────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────┐
│  scene_doc         随磁盘     不依赖 Bevy                          │
│  ── 场景文档模型、属性值、组件注册表、原子存储                     │
└──────────────────────────────────────────────────────────────────┘
```

### 为什么这样分层

| 层 | 为什么独立 | 具体收益 |
| --- | --- | --- |
| `scene_doc` | 持久化格式必须独立于引擎内部类型 | 引擎升级不破坏用户资产；能在无 GPU 环境读写 |
| `editor_core` | 编辑器逻辑要能在 CI 里完整测试 | 156 项测试中有 41 项是这一层的，全部毫秒级完成 |
| `editor_ui` | 界面逻辑（树构建、可用性判定）应可测 | 52 项测试覆盖纯逻辑，不需要窗口 |
| `editor_app` | 只有真正需要窗口/渲染的才碰 Bevy | 上面三层加起来只有一个 crate 依赖 Bevy |

**反例（被否决的做法）**：把逻辑和 UI 混在一起，结果是只能靠手点验证。
本项目刻意把"能测的逻辑"从"必须靠看的绘制"里挤出来 ——
场景树摊平、资源树构建、菜单可用性、视口命中测试、
四元数 ⇄ 欧拉角往返，全都是纯函数并有测试。

### 依赖方向是单向的

```text
editor_app  ──>  editor_ui  ──>  editor_core  ──>  scene_doc
    │                                                  ▲
    └──────────────────────────────────────────────────┘
             （scene_bridge 只用 scene_doc + Bevy）
```

`editor_app` 既依赖 `editor_ui`（要调界面绘制），也依赖 `scene_doc`
（要构建运行时世界）。`scene_bridge` 是唯一直接接触 Bevy 组件的模块，
因此 Bevy 升级的改动集中在这里。

下层**完全不知道上层存在**：`scene_doc` 不知道有编辑器，
`editor_core` 不知道有界面。这是可测试性的来源，也是可替换性的来源
（例如将来换掉 egui，只需重写 `editor_ui`）。

## 三、数据模型

### 3.1 场景文档：扁平实体表 + 父指针

```text
场景文档 {
    格式版本: u32
    元数据:   { 场景标识, 场景名, 保存时间, 自定义 }
    实体表:   { 实体标识 -> 场景实体 }
    顶层顺序: [实体标识, ...]
    资源表:   { 项目相对路径 -> 资源引用 }
}

场景实体 {
    标识: 实体标识           ← 稳定身份，与层级解耦
    名称: String             ← 允许重名，唯一性由标识保证
    父实体: Option<实体标识>  ← 层级是隐式的
    次序: u32                ← 兄弟间唯一，决定顺序
    变换: Option<变换数据>    ← 位置 / 四元数 / 缩放
    组件: Vec<组件数据>       ← 用 Vec 保留用户添加顺序
    编辑器隐藏/锁定/展开      ← 编辑器专有元数据，运行时不用
}
```

#### 为什么不是嵌套的 `children: Vec<场景实体>`

直觉上场景是棵树，嵌套结构最自然。但编辑器里最常见的三种操作
在嵌套树上都是**最坏情况**：

| 操作 | 嵌套树 | 扁平表 + 父指针 |
| --- | --- | --- |
| 拖放改变层级 | 跨树搬移整个子树，重建两处容器 | 改一个 `父实体` 字段 + 整理次序 |
| 按 ID 找实体 | O(n) 遍历 | O(log n) |
| 删除子树 | 递归定位并搬移 | 收集子树后整体移除 |
| 撤销 | 深拷贝两棵树做 diff | 直接换引用 |

**代价**：层级变成隐式的，必须靠 `校验()` 保证：
父实体存在、无环、`次序` 在兄弟间唯一、资源引用已登记。

**这个交换是划算的**：校验只需一次 O(n) 遍历，而所有编辑操作都受益。

**校验不阻止加载**：一个层级轻微损坏的场景，让用户能打开、看到问题、
手工修好，比直接拒绝打开有用得多。唯一的例外是格式版本过新 ——
那属于"语义未知"，必须拒绝。

#### 为什么实体身份用 UUID 而不是场景内序号

序号在删除中间实体后会整体位移，导致撤销栈、资源引用、
外部工具里的引用全部错位。UUID 让身份与位置彻底解耦。

### 3.2 属性值模型：弱类型字段 + 强类型转换

文档里的组件数据是**弱类型**的：

```text
组件数据 { 类型名: String, 属性: Map<String, 属性值> }

属性值 = 布尔 | 整数 | 浮点 | 文本
       | 二维 | 三维 | 四维
       | 颜色 | 枚举 | 资源 | 列表 | 结构 | 空
```

**为什么不用强类型直接序列化**：

1. 引擎类型里有 `Handle<Image>` 这类运行时句柄，序列化它没有意义；
2. 引擎升级会改字段名与结构，用户场景会全部失效；
3. 未知组件无法保留 —— "新版编辑器打开旧场景再保存"会静默丢数据；
4. 编辑器专有元数据会被混进游戏数据。

**代价**：每个类型要写一次 `导出 / 实例化` 转换（见组件注册表）。

**渲染器不用强类型机制表达式**：`属性值` 是一个**完整且封闭**的枚举，
新增一种编辑能力 = 新增一个变体，编译器会强制所有匹配处处理它。
这是"不能漏处理"的编译期保证。

### 3.3 资源引用：路径 + UUID 双层

```text
资源引用值 { 路径: 项目相对路径, 唯一标识: Option<Uuid> }
```

- **路径**保证人可读，且在没有导入元数据时依然可用；
- **UUID**保证改名/移动后仍能重建引用。

两者都失效时，引用进入"缺失"状态并记录在文档校验报告里，
而不是让场景静默加载出一个空组件。

**诚实说明**：本版本**只有路径这一层在真正工作**。
结构上已经同时保存两者，但没有导入器写元数据文件，
因此 `唯一标识` 总是 `None`，"按 UUID 重连引用"尚未生效。
这一点写在 README 与路线图里，没有掩饰。

### 3.4 项目相对路径：在边界处一次性解决三类故障

场景文件里的资源引用有三种典型故障，全部源于"路径就是一串自由文本"：

1. **平台差异**：Windows 写 `textures\hero.png`，Linux 读不到；
2. **绝对路径污染**：把 `C:\Users\某人\...` 存进场景，换台机器立刻失效；
3. **目录穿越**：`../../etc/passwd` 逃出项目根目录。

`项目相对路径` 用不可绕过的构造入口在**边界处**一次性解决：
统一用 `/` 分隔、拒绝绝对路径与前导盘符、拒绝 `..` 与 `.` 段。
**内部字段私有，解析成功即代表路径合法**，后续代码无需重复校验。

这个"在边界处校验、之后靠类型保证"的模式是防止校验逻辑散落的关键。

## 四、修改机制：命令与事务

### 4.1 修改是数据，不是方法调用

需求里有一条硬约束：

> 保存、撤销、重做、复制、粘贴等操作必须共享一致的数据修改规则。

如果"右键删除"调一个方法、"工具栏删除"调另一个方法，
那么撤销栈必须知道两个入口，且两处都要各自维护反操作逻辑。
规模一大，某条路径漏了撤销记录或漏清理选择集，就会出现"撤销后场景错乱"。

**做法**：把修改抽成**枚举值**。

```text
编辑器命令 = 新建实体 | 删除实体 | 重命名实体 | 重设父子
           | 上移实体 | 下移实体
           | 设变换 | 批量设变换
           | 添加组件 | 删除组件 | 设组件属性 | 批量设属性
           | 替换实体 | 设为快照
```

于是所有入口都只做一件事：**构造命令 → 交给 `执行`**。

**收益**：

- 撤销/重做只需要一个实现；
- 命令是纯数据：可序列化、可在测试里直接构造、将来可做宏录制；
- 校验与执行集中在一处，不可能出现两条路径行为不一致。

### 4.2 事务边界：在克隆上执行

`编辑器状态::执行` 做四件事，顺序不可交换：

```text
1. 克隆当前文档
2. 在克隆上应用命令
3. 失败则整体放弃 —— 正本一字未动
4. 成功才提交回正本，并记录撤销条目
```

"在克隆上执行"是同时满足这两个要求的关键：

- 命令**可以**部分执行后失败（例如批量操作中途某项非法）；
- 失败**必须**不留痕迹。

否则就要为每条命令写反向操作，而这正是下面要避开的。

### 4.3 撤销：全量快照 + 命令重放

```text
撤销条目 { 标记: u64, 显示名, 执行前: Arc<场景文档>, 命令, 新实体: Option<实体标识> }

撤销 = 把当前文档覆盖为「执行前」快照
重做 = 重新应用命令（经 重做用命令() 修正）
```

**为什么不用反向操作**：下面这些操作的反向语义都不显然，
任何一处写错就是"撤销之后场景悄悄坏掉"：

- 删除实体连同整棵子树 → 反向要按原次序、原父实体精确复原
- 调整层级 → 反向要复原新旧两侧的次序编号
- 拆除组件 → 反向要复原组件的完整属性表

**本方案的正确性只依赖两件已有测试覆盖的事**：文档能 `Clone`，命令能 `apply`。

**代价是内存**，用字节预算约束（默认 64 MiB、256 步）：
超预算从最旧一端丢弃条目，只影响"能撤销多少步"，
不影响撤销是否正确。

#### 保存点用标记而不是下标

"文档是否已保存"需要记录保存时的栈位置。若用下标，
一旦因预算丢弃最旧条目，所有下标都会位移，保存点就指向错误的条目。
表现为"存过盘的文件仍显示未保存"，或更糟的"没存盘却显示已保存"。

每个条目带一个**只增不减的标记**，比较标记即可。
丢弃条目不影响它 —— 丢弃后保存点标记不再匹配，文档被判为已修改，
这是保守且安全的方向。

#### 重做必须幂等（一个容易漏掉的坑）

`新建实体` 命令的 `指定标识` 首次执行时是 `None`，UUID 由执行过程生成。
若重做时重新执行**原始**命令，就会又生成一个不同的 UUID ——
结果是"撤销再重做之后，实体还在但标识变了"。

后果极隐蔽：所有记录了标识的外部状态（选择集、剪贴板、资源引用、
用户脚本里按标识查找实体的代码）都会静默失效，而文档看起来
"有那个实体"，问题极难被发现。

**解法**：撤销条目记录首次生成的新实体标识，重做时用
`重做用命令()` 把它填回命令的 `指定标识`。

```text
撤销条目.新实体 ──[重做用命令()]──> 编辑器命令::新建实体 { 指定标识: Some(那个标识) }
```

## 五、界面架构：单向数据流

### 5.1 界面不直接改数据

```text
用户操作
  → 面板把操作翻译成 UiAction 排进队列
  → editor_app 在下一帧统一执行
  → 编辑器状态::执行(命令)   ← 唯一允许改文档的入口
```

**三个直接收益**：

1. **可测试**：面板绘制函数可以只检查"点了按钮是否产生了正确的意图"，
   不需要跑起整个 Bevy 应用；
2. **不会在遍历中改容器**：egui 的闭包里拿着文档的不可变借用，
   若在那里直接修改，借用检查器必然拒绝，队列天然避开这一问题；
3. **可以合并与拦截**：将来做"关闭前询问是否保存"，
   只需在执行队列的地方插入判断，不必改任何面板代码。

**代价**：多一层间接，动作在下一帧才生效（用户感知不到）。

### 5.2 界面状态与文档状态严格分开

```text
界面状态 { 停靠布局, 视口相机, 拖拽状态, 搜索关键字, 排序方式, 文本编辑缓冲, ... }
```

这里的东西**都进不了场景文件**。一旦把视口缩放、面板布局混进文档，
保存出来的场景就会带上别人的窗口尺寸，diff 也会被这些噪声淹没。

### 5.3 Inspector 由注册表驱动

```text
组件注册表 { 组件名 -> Box<dyn 组件类型> }

组件类型 trait {
    组件名() -> &'static str
    默认实例() -> Box<dyn Any>
    字段描述() -> &[属性描述]
    导出(&dyn Any) -> Option<Map<String, 属性值>>
    实例化(&mut dyn Any, &Map<String, 属性值>) -> bool
}

属性描述 { 字段名, 显示名, 种类: 属性种类, 默认值, 提示, 只读 }
```

`属性种类` 决定 Inspector 生成哪种控件（布尔→复选框、
浮点→带范围的拖动条、颜色→颜色选择器、枚举→下拉、资源→选择器…）。

**关键效果**：`inspector_panel.rs` 里**找不到任何具体组件的名字**。
所有字段的编辑界面都由描述在运行时生成。支持一个新组件
= 注册一条描述 + 一个转换实现，**不改一行 UI 代码**。

**注册时校验**：每个属性的默认值必须符合声明的种类，
让配置错误在**程序启动时**暴露，而不是等用户点到那个字段才发现。

#### 为什么不用 `bevy_reflect` 作为唯一驱动

反射很强，但覆盖不到编辑器需要的全部类型：`Color`、`Handle<T>`、
`Sprite` 里的枚举、以及游戏自己的组件都需要额外注册。
若 Inspector 依赖反射，"某组件能不能编辑"就取决于它是否恰好派生了
`Reflect`，编辑器对没派生的类型毫无办法。

**反射仍有用武之地**：ECS 调试器（只读浏览运行时世界）会直接走
`bevy_reflect`，因为那里不存在"转换回文档"的需求。

#### 类型擦除带来的不变量（测试守住）

`组件类型` 是类型擦除的，因此"注册表里加了类型、插入逻辑漏了分支"
这件事**编译器抓不到**。后果很隐蔽：注册表里有、属性也写进去了、
运行时统计却把它算成"跳过"，组件静默失效。

这个不变量由一个测试守住：遍历注册表里每个类型，
用声明的默认值走一遍真实的插入路径，断言必须成功。

## 六、持久化：原子保存与恢复

### 6.1 三段式写盘

直接 `File::create(原文件)` 然后写入是危险的：写到一半断电、磁盘满、
进程被 kill，用户唯一的资产就变成半截内容。

```text
1. 写 <场景>.tmp          内容不完整也只污染临时文件
2. 原文件改名 <场景>.bak   保留上一个完好版本
3. .tmp 改名到原文件       原子替换
成功后删 .bak；任一步失败则回滚
```

`sync_all` 是必需的 —— 否则数据可能只在内核页缓存里，
断电后重命名成功但内容是空的。

### 6.2 读取按候选依次尝试

```text
原文件 → .bak → .tmp
```

**每个候选都必须完整解析成功才算数**。
只检查"文件是否存在"是不够的：一个存在但内容损坏的原文件
会让读取提前失败，从而永远用不上完好的备份。

最坏情况只是丢失最后一次保存，而不是丢掉整个场景。

### 6.3 格式版本策略

| 变更类型 | 处理 |
| --- | --- |
| 加字段（新增可选组件字段、新增元数据） | 保持版本号，靠 `serde(default)` 兼容 |
| 改语义（字段单位变化、层级表示变化） | 递增版本号并写升级函数 |
| 读到**更高**版本 | **直接拒绝加载**，并说明文件版本与支持版本 |

拒绝而不是尽力解析，是因为高版本可能引入了本版本不认识的语义变更，
强行解析会在保存时静默丢掉新版数据。

### 6.4 文本格式选择

RON（美化输出，字段一行一个），因为场景文件要进 Git：

```ron
组件: [
    (
        类型名: "Sprite",
        属性: {
            "颜色": 颜色((红: 0.25, ...)),
            "水平翻转": 布尔(true),
        },
    ),
],
```

字段顺序稳定（内部用 `BTreeMap`），保存不会产生无意义的文本 diff。

## 七、运行时：物理隔离

### 7.1 两份数据，一条单向通道

```text
场景文档  ──[构建世界]──►  独立的 Bevy World（运行时宿主持有）
    ▲                            │
    │                            │  只读地取统计数据
    └────── 绝不自动回写 ─────────┘
```

- **文档 → 世界**：只在"开始运行"时发生一次；
- **世界 → 文档**：**默认不存在**。运行时对实体和组件的任何修改
  都停留在那个 `World` 里，停止运行时整个 `World` 被丢弃。

**"运行时乱改不污染编辑器"不是靠约定或小心，而是靠数据被物理隔离。**

### 7.2 为什么运行时世界必须在编辑器主世界之外

如果把运行时实体直接生成在编辑器主世界里，会有两个问题：

1. "停止运行"必须逐个清理，一旦漏掉就留下幽灵实体；
2. 游戏逻辑会直接改到编辑器正在显示的数据。

放在独立的 `World` 里，停止时把它置空，运行时数据**整体消失**，
不存在"清理漏了哪个"的问题。

### 7.3 构建世界分两趟

```text
第一趟：创建所有实体、插入 Name 与 Transform，记录映射
第二趟：按文档里的父关系建立 ChildOf
```

分两趟是必须的：建立父子关系时父实体必须已存在，
而文档里的实体顺序不保证父在子之前（`BTreeMap` 按 UUID 排序）。

**悬空父实体不会让子实体丢失**：父实体不在映射表里时，
保持子实体为顶层实体。丢掉它会让"场景里有 10 个实体，
运行时只有 9 个"难以解释。

### 7.4 运行时实体数的统计口径

实测发现 `World::new()` 本身会创建 **2 个不带任何组件的内部实体**
（索引 0 与 1，没有 `Name`）。它们是引擎基础设施，不是场景内容。

因此 `运行时实体数` 统计"带 `Name` 组件"的实体。
`构建世界` 会给每一个由场景文档创建出来的实体都插入 `Name`，
所以这个判据与"场景实体"的定义严格一致。

若直接用 `entities().len()`，还会踩另一个坑：它返回**曾经分配过**的
索引数量，实体 `despawn` 后索引不回收，因此只增不减。

### 7.5 实体映射表

```text
实体映射表 { 到运行时: Map<实体标识, Entity>, 到文档: Map<Entity, 实体标识> }
```

编辑器需要在两边来回定位（"选中场景树里的某项，高亮运行时对应实体"），
因此这份双向映射是桥接层的核心产物。

## 八、错误处理策略

| 场景 | 策略 | 理由 |
| --- | --- | --- |
| 场景文件解析失败 | 返回带路径与位置的错误 | 用户需要知道是哪个文件、哪一行 |
| 格式版本过新 | 拒绝加载，说明文件版本与支持版本 | 强行解析会静默丢数据 |
| 结构非法（悬空父实体、次序冲突） | 加载但报告，允许用户修复 | 让用户能打开并修好，比拒绝打开有用 |
| 命令执行失败 | 正本不变，错误记入控制台 | 界面层不该看到 `Result`，只需知道"没完成" |
| 保存失败 | 回滚，原文件保持完好 | 用户资产优先 |
| 未注册组件 | 原样保留在文件中，运行时跳过并统计 | 不丢数据，但也不假装它能工作 |
| 内置组件注册失败 | **启动时 panic** | 这是代码错误不是用户错误，应当立刻暴露 |

**统一原则**：面向用户的错误必须携带**可操作的信息**。
"解析失败"是坏错误；"场景格式版本 9999 高于本编辑器支持的 1，
请升级 Bevy Studio"是好错误。

## 九、如何扩展

### 9.1 新增一个可编辑组件

1. 在 `scene_bridge.rs` 定义组件载体类型（若用 Bevy 原生组件则跳过）；
2. 实现 `组件类型`：`组件名` / `默认实例` / `字段描述` / `导出` / `实例化`；
3. 在 `插入已知组件` 里加一条 downcast 分支；
4. 在 `默认组件注册表()` 里注册。

**不需要改任何 UI 代码。** 已有测试 `注册表与插入分支一一对应`
会自动检查第 3 步是否漏了。

### 9.2 新增一条编辑命令

1. 在 `编辑器命令` 加变体；
2. 在 `应用` 里实现，在 `显示名` 里给中文名；
3. 若会产生新实体，在 `新实体` 字段里返回它
   （这样重做才会幂等）；
4. 写测试。

撤销、重做、保存自动生效 —— 因为撤销走的是快照、重做走的是重放。

### 9.3 换掉 UI 框架

`editor_ui` 是唯一依赖 egui 的层。换框架只需重写这一层：
`editor_core` 与 `scene_doc` 完全不知道界面的存在，
现有的 41 + 36 项测试不受影响。

### 9.4 接入游戏运行时（里程碑 C 的方向）

当前 `运行时宿主` 只构建世界与统计。要跑起真正的游戏，需要：

1. 定义游戏插件的加载方式（项目里编译好的 dylib / 静态链接的插件）；
2. 让运行时世界拥有自己的 `Schedule` 并逐帧推进；
3. 把渲染目标接上（去往视口纹理，供编辑器显示）。

**这里必须诚实**：动态库热重载任意 Rust 代码有真实的边界 ——
ABI 兼容性、状态迁移、资源所有权都无法无条件成立
（详见 `功能路线图.md` 的热重载分阶段说明）。
