# 测试计划

本文说明测试策略、自动化测试清单与手工验收清单。

**当前基线（实测）**

```text
cargo test --workspace                    → 156 项全部通过
cargo clippy --workspace --all-targets    → 零警告
```

---

## 一、测试策略

### 1.1 核心原则：把逻辑从绘制里挤出来

绝大多数编辑器的测试困难来源于"逻辑和 UI 混在一起"，
结果是只能靠人手点。本项目的做法是**按可测性设计分层**：

| 层 | 可测性 | 手段 |
| --- | --- | --- |
| `scene_doc` | 完全可测，毫秒级 | 不依赖 Bevy，纯数据结构与文件 IO |
| `editor_core` | 完全可测，毫秒级 | 不依赖 Bevy，用内存存储替身模拟保存失败 |
| `editor_ui` | 逻辑可测 | 把树摊平、过滤、可用性判定、命中测试写成纯函数 |
| `editor_app` | 系统可测 | 用 `World::run_system_once` 在无窗口环境驱动真实系统 |

因此 156 项测试中 **152 项不需要窗口、GPU 或 Bevy 渲染**，
可以在 CI 上以秒级完成。

### 1.2 测试替身的选择

| 真实依赖 | 替身 | 为什么需要 |
| --- | --- | --- |
| 文件系统 | `临时存储`（内存） | 需要注入"写入必定失败"、"原文件损坏"这类现场，真实文件系统做不到可控 |
| 文件对话框 | 后台线程 + channel | 系统测试直接检查 channel 是否收到请求，不弹真窗口 |
| egui 绘制 | 不测绘制，只测其输入逻辑 | 绘制结果无法可靠断言，逻辑已经抽出 |
| 时间 | `Time` 资源 | Bevy 提供，无需替身 |

**注意**：`临时存储` 与 `文件系统场景存储` 的**读取语义必须一致**
（都按 `原文件 → .bak → .tmp` 依次完整解析）。
早期 `临时存储` 只检查"文件是否存在"，导致测试通过但不能证明
生产代码正确 —— 这本身就是个教训，已修正并记录在工作日志里。

### 1.3 测试命名的约定

- 集成测试用 `里程碑A_xxx` / `里程碑B_xxx` 前缀，跑测试时一眼能看出
  覆盖了哪条验收条件（因此该文件允许 `non_snake_case`）
- 单元测试用「行为描述」命名，例如
  `保存点能把文档恢复干净状态`、`重做命令会把首次生成的实体标识填回去`
- 测试名说明**期望的行为**，而不是被测函数名

## 三、手工验收清单

自动化测试覆盖语义，下列检查需要人工确认**观感与交互**。

### 3.1 启动（5 分钟）

- [ ] `cargo run -p editor_app --bin bevy-studio` 能启动
- [ ] 窗口标题是 `Bevy Studio`，尺寸约 1600×950
- [ ] 默认布局是四象限：左场景树、中视口、右检查器、底部资源与控制台
- [ ] 控制台有一条启动日志，没有红色错误
- [ ] 窗口可缩放，面板随窗口调整

### 3.2 里程碑 A 闭环（10 分钟）

- [ ] 「项目 → 新建项目…」→ 输入名称 → 选一个**空目录** → 成功
- [ ] 目录里生成了 `assets/` `scenes/` `src/` 与 `project.ron`
- [ ] 场景树点 `＋` → 出现一个实体，且**自动被选中**（检查器有内容）
- [ ] 检查器里改名称 → Enter → 场景树里的名字变了
- [ ] 「文件 → 保存场景」（Ctrl+S）→ 首次弹文件对话框 → 保存成功
- [ ] 标题栏或状态栏的 `*` 未保存标记消失
- [ ] 关闭编辑器，重新启动，「项目 → 打开项目…」选同一个目录
- [ ] 实体还在，名称、变换、组件都与保存前一致

### 3.3 里程碑 B 场景编辑（20 分钟）

**场景树**

- [ ] 双击实体名进入重命名；Esc 取消恢复原名
- [ ] 右键 → 复制 → 新建出 `_副本` 后缀的实体，名字不重复
- [ ] 右键 → 在此新建子实体 → 新实体嵌在下面且缩进增加
- [ ] 右键 → 上移 / 下移 → 兄弟顺序变化
- [ ] 眼睛图标切换隐藏：实体在视口里消失，名称变暗
- [ ] 锁图标切换锁定：锁定后在视口点击**选不中**它
- [ ] 搜索框输入关键字 → 只显示匹配项**及其祖先**（能看到它所在的层级）
- [ ] 折叠箭头能展开/折叠子树
- [ ] 删除一个有子实体的节点 → 整棵子树消失

**检查器**

- [ ] 未选中时显示"未选中任何实体"的提示
- [ ] 变换的 x/y/z 可以拖动修改，视口里立刻跟着动
- [ ] 旋转以**角度**显示，改角度后视口朝向变化
- [ ] 「添加组件」→ 选 `Sprite` → 出现颜色等字段，且字段有**合理默认值**
- [ ] 颜色选择器可用，改完视口包围框填充色变化
- [ ] 「移除组件」后该组件从检查器消失
- [ ] 缩放改成 0 → 出现"实体将不可见"的警告
- [ ] 「重置为单位变换」能一键复位

**视口**

- [ ] 滚轮缩放**以鼠标位置为锚点**（对象不会跑出屏幕）
- [ ] 中键拖动平移；空格 + 左键拖动也平移
- [ ] 左键点击实体 → 被选中（场景树与检查器同步）
- [ ] 拖动实体 → 对象跟随鼠标，**不漂移**、不飞出去
- [ ] 空白处拖动 → 出现框选矩形，松手后框内实体被选中

## 四、性能测试

### 4.1 已有

| 项 | 方法 | 阈值 |
| --- | --- | --- |
| 序列化线性度 | 100 vs 1000 实体的编码耗时倍数 | < 40 倍（平方复杂度会给出约 100 倍） |
| 撤销栈内存 | 500 次提交后估算占用 | ≤ 预算 + 1 KiB |

### 4.2 计划补充

| 项 | 方法 | 目的 |
| --- | --- | --- |
| 大场景编辑延迟 | 1 万 / 5 万实体下单次属性修改耗时 | 验证"每次编辑克隆文档"的代价是否可接受 |
| 场景树绘制帧率 | 大场景下界面帧耗时 | 验证是否需要虚拟滚动 |
| 场景打开耗时 | 大场景文件读取 + 解析 + 校验 | 建立基线便于回归 |
| 资源扫描耗时 | 5000 个文件的项目 | 目前**每帧扫描目录**，需要评估是否要缓存 |

### 4.3 已知的性能设计取舍

| 取舍 | 现状 | 何时需要改 |
| --- | --- | --- |
| 每次编辑克隆整份文档 | 数百到数千实体是微秒到毫秒级 | 若大场景实测成为瓶颈，改为细粒度命令 diff |
| 资源列表每帧扫描目录 | 小项目无感 | 资源数上千后需要缓存 + `notify` 失效 |
| 撤销栈用 `Arc` 快照 | 64 MiB 预算约束 | 若需要更多撤销步，改用增量快照 |

**注意**：这些是**未实测**的评估，不是已验证的结论。
需求明确要求"优先实现正确性，再根据实际测量进行优化"，
所以尚未做这些优化的原因是**还没有测量数据表明需要**。

## 五、CI 计划

### 5.1 建议的 CI 流水线

```yaml
# 伪代码，本版本尚未配置 CI
steps:
  - 安装 Rust stable
  - cargo fetch --locked              # 验证依赖可解析且与 lock 一致
  - cargo fmt --all -- --check        # 目前未统一格式，见下方说明
  - cargo clippy --workspace --all-targets -- -D warnings
  - cargo test --workspace
  - 断言 Cargo.lock 里只有一个 egui 版本   # 防止版本冲突回归
```

### 5.2 关于 `cargo fmt`

**当前状态：代码未经过 `rustfmt` 统一格式化。**

原因：代码里有大量中文标识符与中文文档注释，`rustfmt` 的换行决策
在中文文本上表现不稳定（会把注释按字节而非显示宽度折行，
有时产生难以阅读的结果）。本项目选择了"人工保持可读性"
而不是"无条件跑 fmt"。

**这是一项技术债**：若团队协作规模扩大，应当：
1. 先试跑 `cargo fmt` 并人工审阅diff；
2. 对确实变差的少数位置加 `#[rustfmt::skip]`；
3. 之后纳入 CI 强制。

### 5.3 无头环境可行性

**已实测**：152 / 156 项测试在没有窗口、没有 GPU 的环境下运行。
需要窗口的只有：

- `bevy_studio` 二进制的单元测试（0 项，无实质内容）
- 无 —— 其余的 `editor_app` 测试都用 `World::run_system_once`，
  不初始化渲染后端

因此 CI 不需要 GPU，也不需要虚拟显示。

诚实列出**没有覆盖**的部分：

| 缺口 | 风险 | 缓解 / 计划 |

## 七、回归时必做的三件事

引擎或依赖升级前，按顺序执行：

```powershell
1. cargo test --workspace                    # 记录基线（应为 156 通过）
2. cargo tree -i egui                        # 确认只有一个 egui 版本
3. cargo clippy --workspace --all-targets    # 应为零警告
```

第 2 步不是多余的：`egui` 的版本冲突会以一堆看似无关的类型错误

## 八、国际化测试

多语言的测试不能只看"源码里有没有中文" —— 用户自定义的中文实体名、
文件路径、技术日志本来就该保留中文。真正要保证的是
**"每一句由编辑器生成的界面文案都走同一套机制、且两种语言都有值"**。

### 词表层（`editor_core::i18n`）

| 测试 | 保证什么 |
| --- | --- |
| `两种语言都有非空文案` | 不存在"只翻了一半"的词条 |
| `词表按键有序且无重复` | 二分查找的前提（顺序错了会**静默**查不到） |
| `键是规范化的小写 ASCII 标识符` | 挡住"把中文原文当键"的回退 |
| `两种语言都能查到每一条词条` | 中英两侧都可查，且结果等于词条值 |
| `英文文案不应与中文完全相同` | 抓"忘了翻译、直接复制中文" |
| `缺失的键返回键本身` | 漏翻时界面显示键名而非静默退回中文 |
| `填充在两种语言下都替换占位符` | 中英占位符个数一致，填充不会错位 |
| `填充参数不足时不会崩溃` | 译文写错不会把编辑器搞崩 |
| `关键界面区域的词条齐备` | **覆盖清单**：菜单栏/工具栏/面板标题/视口/场景树/语言自称 |
| `语言代号往返一致且未知代号回退` | 配置里的未知语言安全回退到中文 |
| `语言自称与反查一致`、`切换语言可往返` | 设置菜单的行为正确 |

### 生成与覆盖核对（`tools/gen_messages.py`）

`python tools/gen_messages.py --check` 做三件事：

1. 词表与 `messages.tsv` 是否一致（防止有人手改生成物）；
2. 词条本身是否规范（键唯一、两种语言都非空、键是小写 ASCII）；
3. **扫描范围内源码出现的每一句界面中文，是否都能在词表里找到词条** ——
   漏翻译在生成阶段直接失败，而不是等用户切到英文才发现。

扫描范围是**已完成改造的文件清单**，而不是整个仓库。
理由写在脚本注释里：核对的目标是"改过的文件不许漏"，
而不是"全仓库不许出现中文"；后者会把用户数据、日志、
尚未迁移的模块全部误报，最后只能靠堆例外让它变绿，那样的检查没有价值。

脚本另有 `应排除` 允许清单（用户数据、序列化字段名、语言自称等），
每条都必须写明理由 —— 不写理由的允许清单会很快变成垃圾桶。

### 应用层（`editor_app/tests/多面板工作区.rs`）

| 测试 | 保证什么 |
| --- | --- |
| `语言偏好能持久化并恢复` | 配置读写 + "切换后重启仍生效" |
| `未知语言回退到中文` | 配置里出现未知语言不崩溃、不卡空值 |
| `损坏的配置回退到默认值且语言回到中文` | 配置坏掉只是丢一次布局，不该连编辑器都开不了 |
| `语言切换动作改变界面语言并标记配置待写` | 菜单动作真的改到状态，且会写盘 |
| `重复设置同一语言是幂等的` | 反复点同一菜单项不会一直写磁盘 |

### 人工验收（无法自动截图的部分）

窗口用 Vulkan 渲染，`PrintWindow(PW_RENDERFULLCONTENT)` 能抓到像素，
但**工具提示、右键菜单、模态弹窗需要交互才会出现**，自动化脚本点不了。
这部分只能人工打开编辑器逐项确认，结论记录在 `工作日志.md`。

**不把单元测试通过当作像素显示正确的证据** ——
单元测试证明"数据对"，截图证明"画出来对"，两者不可互相替代。
